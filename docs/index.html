🔗 Linro#

给长网址做一个好记的入口，用自己的域名管理它。

当前版本：v1.0.2 · English

例如，把 https://www.example.org/a/long/page 变成 https://go.example.com/welcome。以后目标网页搬家，只要在后台修改目标，已经发出去的短链接就能继续使用。

Linro 是开源的短链接管理工具，运行在你的 Cloudflare 账户里。它有中文和英文界面，适合个人或共享工作区的团队。你不用维护传统服务器，但仍需要配置 Cloudflare、域名和登录权限。

可以做什么？#

  • 管理多个短链域名。 配置支持 1–50 个公开域名；每个域名可以独立使用相同短码。
  • 控制链接怎么打开。 选择跳转状态码、按地区选择目标，也可以直接显示纯文本。
  • 给公开访问加规则。 设置密码、到期时间、启停状态、授权请求次数上限，以及可选的浏览器检查。
  • 和团队一起维护。 四种角色控制操作权限；应用令牌让脚本自动管理链接。
  • 整理已有链接。 使用 JSON / CSV 导入导出、批量操作和审计记录。
  • 按需加功能。 访问统计、KV 缓存和浏览器时区采集默认不启用，基础部署先保持简单。

这是一个共享工作区。有读取权限的成员能看到工作区中的链接目标和纯文本内容。公开链接的密码保护不会把这些内容藏起来，也不提供成员之间的数据隔离。了解权限与安全边界

它是怎么工作的？#

把它想成一间有前台和资料柜的小店：

部分 简单理解 Cloudflare 资源
管理后台 你在这里创建链接、设置规则 Admin Worker，附带网页界面
公开入口 访客在这里打开短链接 Redirect Worker
数据库 保存链接、域名、成员和规则的资料柜 两个 Worker 共用一个 D1
登录保护 先确认谁可以进入后台 Cloudflare Access

KV 和 Analytics Engine 是可选服务。默认关闭可选功能能减少额外请求和存储；不代表 Cloudflare 在任何流量、套餐或用法下都免费。实际用量与费用以你的账户和官方计费说明为准。

Linro v1.0.2 使用与部署指南#

English · 回到 README · API 参考 · 离线 HTML

这份指南先教你把项目跑起来，再解释可选功能。所有命令都在包含 package.json 的项目根目录执行。看到 example.com、YOUR_… 或重复数字 ID，表示示例，必须换成你自己的值；它们不是可用账号或凭据。

1. 先认清四个部分#

Linro 像一间小店：Admin Worker 是只给成员使用的柜台，Redirect Worker 是访客打开短链接的门，D1 是共用的资料柜，Access 是检查后台身份的门卫。

名词 你需要知道的事
管理域名 例如 admin.example.com，用于后台和管理 API；整个主机都要由 Access 保护
短链域名 例如 go.example.com，供访客使用；与管理域名分开
短码 slug 域名后的一小段，例如 /welcome；同一域名下不能重复，大小写不同就是不同短码
D1 数据库 两个 Worker 必须使用同一个数据库 ID
应用令牌 token 给脚本使用的钥匙；不是 Cloudflare 部署令牌，也不是访客密码
Secret 放在 Worker 秘密存储里的密钥；不要写入公开配置、网页或 Git
迁移 migration 按顺序给数据库补表、字段和索引；保留数据升级时使用

当前应用版本是 v1.0.2，管理 API 仍是 /Linro/v1。API 的 v1 与应用补丁版本不是同一个编号。源码里有 0001–0006 六份数据库迁移，是否要执行某一份取决于数据库迁移账本。版本兼容说明

2. 先在自己的电脑上体验#

只看界面可直接使用静态演示。下面的本地运行会启动真实应用逻辑和本地数据库，但不会部署到 Cloudflare。

2.1 安装依赖#

先安装 Node.js 22.16.0 或更高版本，解压源码，再进入项目目录。以下基础命令在 Bash 和 Windows PowerShell 都可逐行执行：

node --version
npm --version
node -p "require('./package.json').name + ' ' + require('./package.json').version"
npm ci
npm run toolchain:versions

版本应显示 linro 1.0.2。npm ci 按随包锁文件安装，不要为了处理安装错误而删除 package-lock.json。项目锁定 Wrangler 4.132.0；toolchain:versions 会列出 Wrangler、Miniflare 和 workerd 等实际使用的工具版本。

2.2 准备本地数据并启动#

npm run local:init
npm run build:web
npm run db:migrate:local
npm run db:seed:local
npm run dev:admin

记下 local:init 在你自己的终端中显示的临时开发令牌。再打开第二个终端，进入同一个项目目录：

npm run dev:redirect

用浏览器打开 http://127.0.0.1:8787，输入开发令牌；本地短链入口是 http://127.0.0.1:8788。终端按 Ctrl+C 停止服务。开发令牌保存在本地私有文件中，不要贴到 Issue、截图或提交记录里。

本地数据位于 .local/，与云端 D1 分开。重复 local:init 会保留已有有效密钥和数据，不应靠删除目录来排障。需要测试本地 KV 时可用 npm run local:init -- --kv。本地默认关闭统计与全局时区采集；本地体验不能代替真实 Cloudflare Access、Radar 或网络 RTT 验收。

3. 为正式部署准备 Cloudflare 资源#

3.1 准备清单#

你需要 Cloudflare 账户、已接入 Cloudflare 的域名、可管理 Workers / D1 与 Access 的权限，以及首位管理员能登录 Access 的邮箱。管理域名和短链域名可以是同一根域名下的不同子域名。

本节开始会接触云端。configure、preflight、check、build 主要操作本机；d1 create、db:migrate、secret put 和 deploy 会创建或改变云端资源。逐步执行，确认前一步成功再继续。

3.2 登录部署账户#

npx wrangler --version
npx wrangler login
npx wrangler whoami

检查显示的 Account ID 是你要使用的账户。Cloudflare 的 Account ID、Zone ID、D1 Database ID 和 Access AUD 都不同，不能互相代替。Wrangler 登录是允许电脑部署；它不等于登录 Linro 后台。

若你有多个账户，在创建资源前明确选择。Bash：

read -r -p "目标 Cloudflare Account ID: " CLOUDFLARE_ACCOUNT_ID
export CLOUDFLARE_ACCOUNT_ID

Windows PowerShell：

$env:CLOUDFLARE_ACCOUNT_ID = Read-Host "目标 Cloudflare Account ID"

3.3 创建一个 D1#

只有首次安装才创建新库。 已有实例直接阅读升级。

npx wrangler d1 list
npx wrangler d1 create linro
npx wrangler d1 info linro

记下返回的 database_name 和 database_id，两个 Worker 稍后共用它。不要分别给后台与公开端建库，也不要把本地体验库导入正式库来复制本地 Owner。D1 迁移官方说明

3.4 先给整个后台域名设置 Access#

在 Cloudflare Zero Trust 中创建 Self-hosted Access application：

  1. 主机填写你的管理域名，例如 admin.example.com；Path 留空，覆盖整个主机。
  2. 设置真人 Allow 策略，只允许预期的邮箱或受控身份组。
  3. 选用已配置的邮件验证码或身份提供方。
  4. 保存该应用的 Audience / AUD，以及团队的 https://YOUR-TEAM.cloudflareaccess.com 地址。
  5. 确认公开短链域名没有被此管理应用或上级泛域名策略挡住。

不要用 Bypass 或 Everyone 来“先让后台能打开”。Access 保护外层入口，Worker 还会验证其 JWT。assets.run_worker_first: true 保证后台静态文件也先鉴权；workers_dev 和 preview_urls 均保持 false。Access 应用说明

4. 填配置、迁移，然后上线#

4.1 复制公共模板#

选择一种终端，不要覆盖已有的 deployment.json。

Bash：

test ! -e deployment.json && cp deployment.example.json deployment.json

Windows PowerShell：

if (Test-Path .\deployment.json) { throw "文件已存在，请编辑原文件" }
Copy-Item .\deployment.example.json .\deployment.json

编辑复制出来的文件。下面是可理解的最小起点，其他可选字段沿用模板默认值：

{
  "account_id": "YOUR_CLOUDFLARE_ACCOUNT_ID",
  "database_id": "YOUR_D1_DATABASE_UUID",
  "database_name": "linro",
  "admin_host": "admin.example.com",
  "redirect_hosts": ["go.example.com"],
  "access_issuer": "https://your-team.cloudflareaccess.com",
  "access_aud": "YOUR_ACCESS_APPLICATION_AUD",
  "owner_email": "owner@example.com",
  "analytics_enabled": false,
  "browser_timezone_enabled": false,
  "cloudflare_device_type_enabled": false,
  "redirect_cache_namespace_id": "",
  "source_url": ""
}

所有资源 ID、邮箱和主机都要换成你自己的实际值。主机字段只写域名，不带 https:// 或路径；access_issuer 则需要 HTTPS 且没有结尾 /。source_url 用于给用户提供运行版本的对应源码，正式提供服务前按许可说明填写合适的公开地址。

npm run configure
npm run preflight

configure 会根据 deployment.json 覆盖两份 apps/*/wrangler.jsonc，已有手工配置请先比对。它不会创建 Access、数据库、业务域名记录或秘密。preflight 检查本地配置是否相互匹配；通过不代表远程 DNS、证书、密钥或数据已经可用。

4.2 默认不用填秘密；需要功能时再配置#

普通短链的基础部署可先关闭所有可选功能。需要下列功能时，按对应位置使用 Worker secret，不能放入 deployment.json 的普通字段。

Secret 写入哪个 Worker 作用
LINK_PASSWORD_SECRET Admin 和 Redirect，相同值 验证访客密码，保管好才能继续验证已有密码
BROWSER_CHECK_SECRET Admin 和 Redirect，相同值 给浏览器检查挑战和证明签名
RADAR_API_TOKEN Redirect 单链 VPN 检查需要的 Radar 读取权限
ANALYTICS_API_TOKEN Admin 查询 Analytics Engine 的读取权限
LOCAL_DEV_TOKEN 仅本地开发 正式环境不要设置

首次安装可先部署基础功能，再给已创建的 Worker 添加秘密，刷新后台确认功能可用，最后开启相应设置。新建根密钥可在私有终端生成：

node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"

每一种根密钥各生成一次，保存到自己的秘密管理工具；同一种密钥向两个 Worker 输入相同值。例如开启密码功能：

npx wrangler secret put LINK_PASSWORD_SECRET --config apps/admin/wrangler.jsonc
npx wrangler secret put LINK_PASSWORD_SECRET --config apps/redirect/wrangler.jsonc

按提示粘贴，不把值写在命令参数或文档里。secret put 会创建并立即部署 Worker 新版本，不只是本地登记；已有线上实例应安排好变更时间。浏览器检查使用相同方式写入 BROWSER_CHECK_SECRET。升级时保留原根密钥，不要重新生成。 根密钥需为 43–128 个 base64url 字符，与每条短链的访客密码不同。Worker secrets 官方说明

4.3 应用全部待处理迁移#

迁移像给资料柜增加抽屉。已有资料不能通过重新建柜或重复初始化来“升级”。先检查目标数据库，再执行：

npx wrangler d1 migrations list DB --remote --config apps/admin/wrangler.jsonc
npm run db:migrate
npx wrangler d1 migrations list DB --remote --config apps/admin/wrangler.jsonc

本版包含：

迁移 增加什么
0001_initial.sql 基础表、索引和最后一名 Owner 的保护
0002_link_controls.sql 地区规则、密码、次数上限和规则修订
0003_text_responses.sql 纯文本模式
0004_browser_checks.sql 单链 block_vpn 开关
0005_link_kv_cache.sql 每条链接自己的 KV 时长
0006_destination_hosts_and_archive.sql 目标主机索引、冲突约束和日归档排序索引

迁移失败就停下来处理原因，不删除账本或跳过失败项。npm run deploy 不自动创建数据库，也不自动执行迁移。

4.4 检查并部署#

npm run check
npm test
npm run test:runtime
npm run build
npm run test:browser
npm run deploy:dry-run

test:runtime 使用原生 workerd；test:browser 需要真实 Chrome / Chromium，可以通过 CFL_CHROMIUM_PATH 指向你已安装的浏览器。工具无法启动应记录为未完成，不能当作测试通过，也不要关闭浏览器安全限制来凑结果。deploy:dry-run 只验证打包，不切换线上流量。

确认配置、迁移和检查结果后：

npm run deploy

该命令实际执行：预检查 → 构建 → 单元测试 → 原生运行时测试 → Admin 发布 → Redirect 发布 → 公开探活。它不包含浏览器测试。两个 Worker 的发布不是原子操作，其中一个失败不会自动回滚另一个。

Admin 保留 compatibility_date: "2026-09-15" 与 enable_request_signal，让调用方断开连接时可取消统计上游请求。不要只删除此标志而保留旧日期；配置生成器与预检查负责保持一致。

4.5 第一次打开后台#

用 owner_email 对应的 Access 身份登录。只有数据库用户表为空时才会自动建立第一名 Owner；已有用户时，修改配置中的邮箱不会替换原 Owner。

在“域名”页添加已经绑定到 Redirect Worker 的主机，再创建测试链接。平台上的域名绑定与 Linro 的域名记录是两件事，缺一不可。 多域名时，先把 1–50 个主机写入 redirect_hosts、重新配置并发布 Redirect，再到后台逐个登记；相同短码可以在不同域名下使用。后台新增域名不会自动创建 DNS、证书或 Worker Custom Domain。Custom Domains

为了运行下面的专用检查，创建 slug=docs、目标 https://example.org/docs、状态码 301、cache_ttl=0 的普通无保护测试记录，然后替换命令中的公开主机：

npm run verify:deployment
node scripts/smoke.mjs --short-url https://go.example.com/docs --expected-location https://example.org/docs --code 301

检查只验证首跳，不跟随目标。GET /health 显示公开端版本，但不查 D1；应同时验证一条实际短链。首次测试通过后可删掉专用记录，再逐个打开需要的可选功能。

5. 日常使用与团队权限#

5.1 创建链接时先看这几个选项#

选项 新手可以这样理解
域名与短码 合起来是发给别人的地址。短码为空会自动生成 8 位
目标 URL 访客最终要打开的 HTTP(S) 地址；不支持把用户名或密码写进 URL
301 / 308 永久跳转，客户端可能记住；目标还会调整时应谨慎使用
302 / 307 临时跳转，适合需要改目标的入口；创建时可明确选择 302
到期与停用 到期或停用后，访客不能再正常打开
最大授权请求次数 控制服务器放行次数，不是独立访客人数；符合条件的 HEAD 也会扣一次
纯文本 直接显示一段文字，不把它当 HTML 执行
浏览器缓存 cache_ttl 访客电脑能保留跳转多久，默认 0。需要快速撤回时保持 0

短码允许 1–64 个 ASCII 字母、数字、_ 和 -。health、cdn-cgi 和 __Linro_ 前缀保留，判断保留项时忽略大小写；Linro 可以作为业务短码。

5.3 自动化需要两把钥匙#

脚本先用 Access Service Token 通过外层门卫，再用 Linro 应用令牌决定可以操作什么。请在同一 Access 应用为指定 Service Token 设置 Service Auth 策略；只创建令牌还不够。官方 Service tokens 说明

应用令牌只允许 links:read、links:write、links:delete、domains:read、analytics:read，且不得超过用户当前角色。所有应用令牌，包括 Owner 创建的令牌，只能修改该用户自己创建的链接。同一用户的多个令牌共享此写入范围，需要隔离自动化责任时应使用独立用户。

令牌有效期是创建时起 60 秒至 365 天；每个用户最多 50 条未撤销记录，过期但未撤销的也计数。完整值只显示一次，之后只能撤销并重建。具体调用见 API。

5.4 编辑、导入和导出#

多人编辑时，version 像每份资料的修订号码。看到 409 冲突，先刷新并比较修改，再保存；不要忽略冲突重发旧对象。

导出支持 JSON 和 CSV，文件包含目标、描述和纯文本等实际业务内容，按私有备份保管。导出不含密码及其校验串；需要完整恢复密码功能时，必须使用 D1 备份和原根密钥。GUI 导入将数据转换成创建字段，文件最多 2 MiB（2,097,152 字节）、5,000 条，每次提交 10 条；整个文件不是一个事务。

每个 API 导入批次要么全部成功，要么都不写入。GUI 对明确发生在写入前的限流可等待重试，并保留已完成进度。遇到断网或超时而结果不明，先检查哪些短码已创建，再决定重试；项目没有通用写入幂等键。批量启停/删除则逐项返回结果，可能部分成功。导入格式示例

6. 可选功能：需要什么再开什么#

6.1 密码、地区规则和纯文本#

密码长度为 12–128 个 JavaScript 字符串代码单元，且最多 512 UTF-8 字节，不能包含控制字符；不自动去掉首尾空格。编辑时选择“保留”“设置”或“移除”；API 中省略 password 是保留，null 是移除，空字符串无效。

密码通过后，页面先回到同源短链再请求目标，密码不会随跳转发给目标网站。解锁 Cookie 最长 900 秒，规则变更会让旧证明失效。已有密码依赖原 LINK_PASSWORD_SECRET，丢失根密钥不能从数据库找回明文。

地区规则最多 32 条，按“国家 → 大洲 → 默认目标”选择，来源为 Cloudflare 元数据。它只决定去哪里，不证明用户身份。纯文本最多 16,384 个代码单元、32,768 UTF-8 字节；不能同时保留地区规则，查询参数固定丢弃，最终响应始终 no-store。

6.2 浏览器时区和单链 VPN 检查#

全局 browser_timezone_enabled 默认 false。普通链接只有在全局采集开启、Analytics 开启且 Redirect 有可写 Analytics 绑定时才增加采集页面。单链 block_vpn=true 独立生效，即使全局采集关闭也会要求检查。

浏览器用 Intl.DateTimeFormat().resolvedOptions().timeZone 自报时区；IP 时区来自 request.cf.timezone，不是浏览器时区。源码以 request.cf.country === 'T1' 判断平台 Tor 标记。自报时区不可信，旅行、系统设置和 IP 数据误差都可能造成误拦。

开启单链检查前，两端需有 BROWSER_CHECK_SECRET，Redirect 还需有账户 Radar 读取令牌：

npx wrangler secret put RADAR_API_TOKEN --config apps/redirect/wrangler.jsonc

该策略只接受 Radar 分类 ACCESS_ISP 或 ORGANIZATION 的 ASN。Worker 在一条同源 WebSocket 上发出 5 轮随机挑战，浏览器逐条原样回传。每次收到正确回包后等待 400 ms 再发下一轮。Worker 计时并与该连接的 TCP 或 QUIC RTT 比较。五轮全部完成且至少一轮的绝对差严格小于 55 ms 才通过；恰好 55 ms 不算通过。缺失时区、分类、RTT 或有效证明也可能被拒绝。它是严格的可选启发式策略，不保证准确识别所有 VPN；企业、校园网络、繁忙设备或排队也可能失败。

挑战和证明最长 120 秒，签发证明不会续期；它们绑定链接规则、主机、查询和网络上下文。源码没有服务端一次性消费表，不能承诺绝对防重放。无 JavaScript、Cookie 被禁用、网络变化或过期会阻止流程。HEAD 在只有全局采集时可以跳过采集；单链阻止开启且无证明时返回 403。

6.3 KV：辅助缓存，不是数据库替身#

redirect_cache_namespace_id 留空表示不用 KV。需要时先创建 namespace：

npx wrangler kv namespace create REDIRECT_CACHE --config apps/redirect/wrangler.jsonc

把返回的 ID 填入配置、重新生成并发布两端，确保它们绑定同一 namespace。全局 TTL 默认 300 秒，范围 60–86,400 秒。单链 kv_cache_ttl 留空/null 继承，0 禁用，其他值也须在此范围。

密码、有效时区采集、VPN 检查、次数上限、到期、地区分流和纯文本链接都绕过 KV。普通命中仍核对最新 D1；D1 失败不会用旧缓存放行。KV 故障可以回到 D1，KV 写入失败有冷却抑制。

不开 KV 的普通直跳只需一次 D1 查询。开 KV 后还可能多一次 KV 读取、回填和安全复核；不同实例会有自己的缓存。因此 KV 并不必然省钱或更快，应比较真实延迟、D1 rows_read 和 KV 操作数，再决定是否启用。KV 计费 · D1 计费

6.4 访问统计与日归档#

统计默认关闭。需要时将 analytics_enabled 改为 true，确认 dataset 名称，并给 Admin 配置有 Account → Account Analytics → Read 权限的令牌：

npx wrangler secret put ANALYTICS_API_TOKEN --config apps/admin/wrangler.jsonc
npm run configure
npm run preflight

重新发布后，只有 Redirect 绑定写入端 ANALYTICS；Admin 使用读取 secret 查询。打开统计前确认当前套餐、账户权限和费用。Analytics Engine SQL API

统计中的“点击”是最终获准的业务 GET 的采样加权值，不是独立访客数。HEAD、密码提交和浏览器检查中间步骤不记成功点击。事件不保存原始 IP、完整 User-Agent、目标 URL、正文、Cookie 或密码；来源只取主机名。

仪表盘用 view=dashboard，只查趋势和总数；完整统计查多个维度，最多两路并发，整组有 10 秒上游时限。同实例的相同成功结果最多复用 15 秒，请求仍检查权限和 link_ids。available:false 表示未配置，不是零访问；查询错误也不能当作零。

浏览器时区与 IP 时区分开存储：blob6 是 IP 参考时区，blob9 是浏览器时区；blob7 是设备分类。默认设备为 none。只有确认平台可信地产生并覆盖 CF-Device-Type 时，才打开 cloudflare_device_type_enabled；mobile/tablet 映射为 mobile，desktop 映射为 pc。

归档开关 analytics_rollup_enabled 默认 true，但只有统计启用时才实际启用 Cron。默认每 15 分钟运行，允许 5 / 15 / 30 / 60 / 360 / 1440 分钟；默认每 6 小时重算已完成窗口。首次从最近两个完整 UTC 日开始，后续按水位追赶；每批最多 400 个链接/日期组合，计数变化才更新。归档只保留每日点击，没有完整维度，也不是查询失败时自动替代实时统计的后备系统。

6.5 限流与资源使用#

应用自带四个独立限流 namespace：认证前、后台写入、公开请求、密码尝试。默认密码桶使用来源 IP 的 SHA-256 哈希作为 key，每个 key、每个 Cloudflare 位置 5 次 / 60 秒。共享出口可能共用额度；它不是连接级计数，也不是全球单一原子计数器。官方限流语义

有需要时，可在账户支持的 WAF 中另加只针对密码 POST 的规则：

(http.host eq "go.example.com" and http.request.method eq "POST" and starts_with(http.request.uri.path, "/__Linro_unlock/"))

替换主机后再配置适用的计数键、窗口和动作。项目不自动调用 Cloudflare 账户创建规则，也不能承诺免费计划支持所需 WAF 功能。不要把普通 GET 和静态资源塞进很低的密码桶。

减少资源消耗的起点是：先不开不需要的 KV、统计、采集和归档；使用界面默认游标分页；按需要清理旧审计/归档/撤销令牌；不要高频轮询完整统计。Admin 静态资源先经过 Worker 鉴权，因此也会执行 Worker；这是后台保护的一部分，不要为了省请求绕过它。

7. 备份与保留数据升级#

7.1 先保存资料#

升级前保管当前配置、资源 ID、两个 Worker 的版本 ID、域名/Cron/绑定，以及根密钥。密钥与数据库备份分别安全保管。选择新的私有文件名导出 D1：

npx wrangler d1 export DB --remote --config apps/admin/wrangler.jsonc --output Linro-pre-upgrade-backup.sql

npm run backup 也可导出，固定输出 Linro-backup.sql，再次运行前先归档旧文件。SQL 备份含真实用户、链接、审计和校验值，不能上传公共仓库。

恢复演练使用新建的隔离数据库，先验证、后删除旧资料；明确记录目标库的显式 ID，不要凭相同名称猜测目标。对备份做完整性检查，确认域名、链接数、规则及原密钥能配合工作，再考虑正式恢复。代码回滚不会恢复数据库。

7.2 把新源码接到原来的资源上#

从 v1.0.1 升到 v1.0.2，保留原 Worker 名、D1 ID、KV namespace、dataset、Access、域名和根密钥。不要把公开占位模板直接部署到已有实例；也不要把旧版本目录里的整个生成配置盲目覆盖回来，应比较并补上新版本要求。

确认备份后，查询全部待应用迁移：

npx wrangler d1 migrations list DB --remote --config apps/admin/wrangler.jsonc
npm run db:migrate
npx wrangler d1 migrations list DB --remote --config apps/admin/wrangler.jsonc

数据库已有 0001–0006 时没有新增迁移要执行；较早数据库补缺失项。不能据版本号推断实际迁移状态。以下只读 SQL 可帮助核对：

npx wrangler d1 execute DB --remote --config apps/admin/wrangler.jsonc --command "SELECT name FROM d1_migrations ORDER BY id;"
npx wrangler d1 execute DB --remote --config apps/admin/wrangler.jsonc --command "SELECT name,type FROM pragma_table_info('links');"
npx wrangler d1 execute DB --remote --config apps/admin/wrangler.jsonc --command "SELECT sql FROM sqlite_master WHERE type='trigger' AND name='links_rule_revision';"
npx wrangler d1 execute DB --remote --config apps/admin/wrangler.jsonc --command "PRAGMA foreign_key_check;"
npx wrangler d1 execute DB --remote --config apps/admin/wrangler.jsonc --command "SELECT key,value,updated_at FROM settings WHERE key LIKE 'analytics_rollup_%';"
npx wrangler d1 execute DB --remote --config apps/admin/wrangler.jsonc --command "SELECT link_id,date,clicks,updated_at FROM daily_stats ORDER BY date DESC LIMIT 10;"

然后重新运行第 4 节的本地检查、原生测试、浏览器测试和 dry-run，再发布两个 Worker。不要重复生产 seed，也不要清空用户表重新生成 Owner。

7.3 上线后确认，再处理旧版本#

检查两个 Worker 的实际版本、流量、绑定及域名，并验证已有应用令牌、密码短链和浏览器检查。v1.0.2 继续使用 v1.0.1 的 API、令牌哈希、Cookie 名称和兼容键。旧 RTT 回执及 VPN 通行证明失效，重新打开短链可开始新挑战。

需要精确分版本上线时，可使用 Wrangler 的版本上传与切流功能；先记录每个 Worker 返回的 UUID，并按官方版本部署说明核对绑定和配置。不要把 --keep-vars 当作保留所有配置的承诺。

若部署已成功但探活失败，先查 DNS、TLS、域名绑定和版本，再单独运行 npm run verify:deployment。它不做自动重部署，也不关闭证书校验。确需回滚时，先确认旧代码仍兼容当前数据和密钥，再把两个 Worker 切回已记录版本；不要用旧备份直接覆盖升级后的新增业务数据。

Linro v1.0.2 API 参考#

English · 部署与使用 · 权限说明 · 安全边界

API 就是让程序填写和读取表单的入口。如果只是日常管理，用网页即可；写脚本时，先读“共同规则”，再找对应接口。本页按当前源码列出 25 个管理方法/路径组合，以及公开短链协议。

所有域名、邮箱、UUID 和请求 ID 都是示例。凭据从你自己的秘密管理工具读取；本文不提供可用 token 或密码。

1. 先理解共同规则#

地址与两层认证#

管理 API 的基础地址是 https://admin.example.com/Linro/v1。后文 /links 表示完整地址末尾再接 /links。替换自己的管理主机，保留路径大小写，不额外加结尾 /。基础地址本身不是接口目录；不支持的方法或路径返回 404 api_not_found。

生产请求先经过 Cloudflare Access，再经过 Linro 自己的权限检查。浏览器使用真人 Access 会话；脚本使用 Access 服务身份加 Linro 应用令牌。

请求头 何时需要
Accept: application/json 管理客户端建议发送；不会把登录跳转变成成功 JSON
Content-Type: application/json 带 JSON 正文的管理写请求，可附 charset=utf-8
Authorization: Bearer Linro_… 脚本使用的完整 Linro 应用令牌
CF-Access-Client-Id / CF-Access-Client-Secret 脚本通过外层 Access；该服务身份必须被应用策略允许
Cf-Access-Jwt-Assertion Worker 验证的 Access JWT，正常由认证入口传入，不要自己伪造
Origin / X-Linro-CSRF: 1 真人 Access 会话写请求，Origin 必须等于管理 origin
X-Linro-Dev 仅受限的本地开发模式，正式请求不要使用

API 入口拒绝显式不等于 ADMIN_ORIGIN 的 Origin，包括空字符串或 null。服务端 token 请求可以不发 Origin；真人写入还拒绝 Sec-Fetch-Site: cross-site。应用 token 不走真人 Cookie 的 CSRF 分支，但仍受入口来源限制。

没有开放的跨站 CORS/JSONP 协议，也没有通用 OPTIONS 预检接口。把 token 放进外站网页不能绕过这些限制。请求一旦带 Authorization，就按 token 分支认证；无效 token 不会回退到浏览器 Cookie 登录。

权限与所有权#

scope 是某项操作的许可证。应用令牌只能具有 links:read、links:write、links:delete、domains:read、analytics:read，并受所属用户当前角色限制。

工作区读取共享。Editor 与全部应用令牌只能修改所属用户自己创建的链接；真人 Admin/Owner 可维护整个工作区。相同用户的两个令牌共享用户级写入范围，并非每枚令牌各自隔离。标记“交互式”的接口不接受应用 token。

成功和失败长什么样？#

正常读取/修改通常返回 200，创建/导入返回 201。管理成功统一包装为：

{"ok":true,"data":{"deleted":true}}

错误示例：

{"ok":false,"error":{"code":"version_conflict","message":"This item changed. Refresh before saving again.","request_id":"example-request-id"}}

data 可能是对象或数组，不能总假设有 items。程序按 HTTP 状态和 error.code 判断，英文 message 供排障。通过 Worker 安全包装的响应有 X-Request-Id；反馈问题时给这个 ID，不给凭据。

管理 JSON 使用 Cache-Control: no-store。限流 429 带 Retry-After: 60。外层 Access 或平台提前返回的结果可能是 HTML/302，没有这套 JSON；解析前检查状态和 Content-Type，不要自动跟随认证重定向。

正文、时间和编辑版本#

JSON 正文最多 262,144 字节，按实际读取字节计算；必须是有效 UTF-8 对象，不能为数组或 null。写接口的顶层正文拒绝未声明字段，不要把 GET 的整份对象直接 PATCH 回去；嵌套条目按各接口规则处理。

数字用 JSON 数字。业务布尔一般接受 true/false/1/0；reset_redirect_count 只接受布尔。字符串长度通常按 JavaScript UTF-16 代码单元算，密码和正文还受单独 UTF-8 字节限制。

created_at、updated_at、expires_at、revoked_at 是 Unix 秒，不是毫秒。导出包 exported_at 是 ISO 时间字符串，日归档 date 是 UTC 日期。null 的意思由字段决定，不能通用地当成“不修改”。

链接、域名、用户更新带当前 version；链接和域名删除带 ?version=…。它像取号：别人先改过，旧号码就会得到 409。刷新、比较后再提交。它不等于访客保护使用的 rule_revision。

分页：选一种方式#

方式 请求 响应
游标，适合连续翻页 pagination=cursor&limit=25；下一次原样带回 cursor items, limit, next_cursor，末页 next_cursor:null
页码，兼容旧客户端 默认或 pagination=page&page=1&limit=25 items, page, limit，部分接口另有 total

limit 默认 25，范围 1–100；页码范围 1–100000。游标模式不能同时带 page，页码模式不能带 cursor。游标最长 512 字符，应当作不透明值传回；保留原筛选条件，不用于权限证明或快照一致性。

链接列表可用 include_total=true/false 控制计数，页码默认 true、游标默认 false。审计只有页码模式返回总数；日归档没有总数。域名、用户、令牌和设置直接返回数组，不使用这套分页。

三个健康入口别混淆#

地址 认证/方法 检查什么
Admin /health 已认证，GET/HEAD 后台浅层健康
Admin /Linro/v1/system/health Owner，GET Worker 和 D1 SELECT 1
Redirect /health 公开，GET/HEAD 公开端浅层状态和版本，不查 D1

管理 API 不自动把 HEAD 当 GET：例如 HEAD /Linro/v1/links 返回 404。

2. 链接表单与返回对象#

创建和更新可填写的字段#

POST /links 与导入条目支持下面 17 个字段。PATCH /links/{id} 还需 version，并允许 reset_redirect_count。更新时省略字段通常保留原值。

字段 规则 创建默认 / 特别说明
domain_id 现有域名 ID，字符串最长 36 必需；停用域名也可存链接，但访客不能使用
slug 1–64 个 ASCII 字母、数字、_、- 省略或空串自动生成 8 位；更新空串无效
target_url HTTP(S)，原始输入与规范化后的 URL 都最长 4096 redirect 模式必需；拒绝凭据、控制字符和反斜线

description 字符串最长 2000，可正常换行 空串

enabled 布尔或 0/1 1；读取为数字
expires_at null 或 Unix 秒整数 1–253402300799 null；过去时间允许保存，但公开访问已过期
cache_ttl 整数 0–3600 秒 0；控制客户端缓存，不是 KV

目标还需通过私有主机和短链环路策略。验证不会请求目标网页，也不解析 DNS。短码保留 health、cdn-cgi 和 __Linro_ 前缀，保留比较忽略大小写；业务短码本身区分大小写。Linro 可用；含点的 robots.txt 不符合短码语法。

查询参数怎样带过去？#

只处理部署白名单允许的来访键，敏感键不能转发：

  • discard：保持已保存目标的查询参数，丢弃来访参数。
  • merge：只追加目标中尚不存在的允许键，目标已有同名值优先。
  • replace：用过滤后的来访参数替换目标的整个查询部分；来访为空会清空。

敏感登录、重置或回调目标要求 discard。内部 _Linro_check、_Linro_lang 不透传。最终组合 URL 最长 8192 字符，超长返回 414。

地区规则 GeoRule#

[
  {"kind":"country","code":"JP","target_url":"https://www.example.org/ja/"},
  {"kind":"continent","code":"EU","target_url":"https://www.example.org/eu/"}
]

条目只接受 kind,code,target_url。优先级为国家 → 大洲 → 默认目标；相同 kind:code 不可重复。大洲为 AF/AN/AS/EU/NA/OC/SA；国家要求大写两字母且非 XX，代码不做完整 ISO 名单核验，调用方应填真实有效国家代码。每个目标都应用同样安全检查。text 模式必须显式清空原地区规则。

读取到的 PublicLink#

“PublicLink”是管理 API 中移除密码校验信息后的对象名称，不意味着匿名可读。它包含业务字段，但不含 password/password_hash；还包括：

字段 意思
id、hostname、short_url 链接 UUID、主机、短地址；生产 short_url 为 HTTPS
password_protected 是否有密码保护，布尔值
created_by 创建用户 UUID，历史记录可能 null
created_at、updated_at Unix 秒
version 编辑并发检查版本
rule_revision 缓存和访客证明使用的规则修订
redirect_count 有限额业务请求的授权计数，不是总点击量
remaining_redirects 无限时 null，否则 max(0,max_redirects-redirect_count)
domain_enabled 链接列表含此字段，其他返回不保证包含

enabled 和 block_vpn 输出 0/1；geo_rules 输出数组。text 模式对外 target_url:""，数据库内部的 about:blank 只是兼容存储值，不会被打开。

示例 ID 约定：域名 11111111-1111-4111-8111-111111111111，链接 22222222-2222-4222-8222-222222222222，用户 33333333-3333-4333-8333-333333333333。实际调用必须替换为 API 返回值。

3. 全部管理接口#

以下描述的返回值都是外层 data，省略重复的 ok:true。{id} 是实际资源 ID，调用时不带花括号。

GET /session：我是谁，能做什么？#

任意已认证会话可用，无额外 scope。返回：user、scopes、source_url、auth_kind（access/token/local）、site_name、analytics_configured、link_write_scope（owned/workspace）、version:"1.0.2"，以及下面的功能和策略对象：

{
  "features":{
    "browser_timezone_collection_enabled":false,
    "browser_checks_configured":false,
    "redirect_cache":false,
    "cache_consistency":"d1-guarded",
    "redirect_cache_default_ttl":300,
    "passwords_configured":false,
    "text_responses":true,
    "device_header_enabled":false
  },
  "security":{
    "queryKeys":["utm_source","utm_medium","utm_campaign","utm_term","utm_content"],
    "expiredStatus":404
  }
}

这些是结构示例，实际值以部署为准。全局采集标志反映 Admin 中的采集与统计开关，公开端执行还要求真实 Analytics 写入绑定。passwords_configured 和 browser_checks_configured 只检查 Admin 本侧根密钥格式，不证明两端值相同、Redirect 绑定完整或访客流程已经可用。会话不返回根密钥、Access 凭据、私有目标白名单或令牌明文。

GET /summary：工作区有多少链接？#

需 links:read。返回 {"links":6,"active":5,"expired":1,"domains":2}。active 要同时满足链接/域名启用、未过期和未耗尽；expired 单独按时间统计，不保证与其他状态互斥。

GET /links：列出链接#

需 links:read。支持两种分页，按 created_at DESC,id DESC 排序。

查询参数 规则
pagination,page,cursor,limit 见共同分页规则
view full 默认完整对象；picker 仅 id,hostname,slug
include_total 字符串 true/false；页码默认 true，游标默认 false
q 搜索 slug/title/target_url；转义后的 LIKE 模式含两侧 %，最多 50 个 UTF-8 字节
domain_id 按域名 ID 过滤，未知 ID 通常得到空列表
status all/active/disabled/expired/exhausted

游标响应为 {"items":[],"limit":25,"next_cursor":null}，仅要求计数时附 total。页码响应含 page；默认附 total。搜索上限按实际模式字节而非“50 个汉字”，超出为 400 search_too_long。

POST /links：创建一条链接#

需 links:write。接受第 2 节创建字段，返回 201 PublicLink。

{"domain_id":"11111111-1111-4111-8111-111111111111","slug":"welcome","target_url":"https://www.example.org/start","title":"欢迎页","redirect_code":302,"cache_ttl":0}

创建者由认证身份决定，不能自行填写。自动短码冲突最多尝试 5 轮；显式短码冲突返回 409。无域名为 400 domain_not_found；需要的根密钥未配置会失败，不降级为明文。链接和成功审计同批提交。

GET /links/{id}：读取一条链接#

需 links:read。返回 PublicLink，不存在为 404。可读取他人创建的工作区链接；不会返回密码校验串。

PATCH /links/{id}：改一条链接#

需 links:write，同时检查所有权。提交当前 version 和要改的字段：

{"version":1,"title":"新标题","target_url":"https://www.example.org/new","cache_ttl":0}

返回更新后的 PublicLink。重置次数可传 reset_redirect_count:true；移除密码传 password:null。找不到为 404，版本旧为 409 version_conflict，跨所有者为 403 link_owner_required。

改域名/短码后先提交 D1，再尽力清除旧 KV；两种存储不是跨服务原子事务，旧缓存仍受最新 D1 校验。已经发给客户端的响应不能强制收回。

DELETE /links/{id}：删除链接#

需 links:delete 和所有权，必需 ?version=1，无正文。成功 {"deleted":true}；不存在 404、版本冲突 409、无权 403。D1 日归档随外键级联删除，已经写出的 Analytics Engine 历史事件不会由这个接口清除。

POST /links/import：小批量创建#

需 links:write，顶层仅 links，数组 1–10 项，每项为创建字段：

{"links":[{"domain_id":"11111111-1111-4111-8111-111111111111","slug":"notice","response_mode":"text","text_content":"维护已完成。","geo_rules":[]}]}

成功 201，返回 {"imported":1,"ids":["22222222-2222-4222-8222-222222222222"]}。本请求先校验全部条目，再事务提交；其中一条验证/唯一性失败则本批不部分导入。它不接收 CSV、multipart、只读导出字段、domains 或 settings；GUI 在客户端完成文件转换和分批。

POST /links/bulk：批量启停或删除#

正文只含 action,items。action 为 enable/disable 时需 links:write，delete 时需 links:delete；每项都检查所有权。items 为 1–10 个不重复的 {id,version}：

{"action":"disable","items":[{"id":"22222222-2222-4222-8222-222222222222","version":1}]}

返回 200 {"results":[{"id":"22222222-2222-4222-8222-222222222222","ok":true}]}。失败项可能带 forbidden:true 或 conflict:true。200 不等于每一项都成功，逐项处理也不整体回滚；先检查 results 再向用户确认。

GET /domains：列出域名#

需 domains:read，无分页。默认按 hostname 排序返回完整 Domain 数组及 link_count，包括停用域名。view=directory 只返回 id,hostname,enabled,default_redirect_code，适合选择框并减少计数查询；无单独 GET /domains/{id}。

POST /domains：登记业务域名#

需 domains:write，当前仅真人 Admin/Owner 可满足。只接受 hostname、name、enabled、default_redirect_code：

{"hostname":"go.example.com","name":"公共入口","enabled":true,"default_redirect_code":302}

hostname 必需，最长 253 字符，只写规范域名，不带协议、端口或路径。name 默认空且最长 100，enabled 默认 1，状态码默认 301。返回 201 Domain，不保证带 link_count。重复主机为 409；管理主机为 400 admin_hostname；已有链接默认/地区目标使用此主机时为 409 hostname_is_destination，先迁移目标避免短链环路。

这个接口只写 D1，不配置 DNS、证书或 Worker 绑定。

PATCH /domains/{id}：改域名设置#

需 domains:write。只接受 version、name、enabled、default_redirect_code：

{"version":1,"name":"团队入口","enabled":true,"default_redirect_code":302}

返回 Domain。hostname 不可修改，传入会 400；不存在 404，版本冲突 409。停用影响其下全部链接；默认状态码只影响以后新建且未指定码的链接。

DELETE /domains/{id}：删除域名记录#

需 domains:write，查询必需 version，无正文。成功 {"deleted":true}。仍有链接引用时 409 in_use，需先移动或删除链接；不会自动清除平台 DNS 或 Custom Domain。

GET /stats：查实时统计#

需 analytics:read。默认 view=full，view=dashboard 只返回总量/趋势和共同元数据，减少查询量。

参数 规则
days 默认 7，整数 1–90；以 UTC 分组
view full/dashboard，只允许出现一次
link_id 一个小写标准 UUID
link_ids 逗号分隔 1–50 个小写标准 UUID

两种 ID 参数互斥，各自不能重复出现；空串、空项或尾逗号无效。50 项先计数再去重。都不传表示整个工作区；显式选择中有任一 ID 不存在，404 stats_link_not_found，即使未配置统计也先检查选择。days 当前按第一个值解析，调用方仍应只发一次。

未配置返回 200，而不是错误或零访问：

{"available":false,"reason":"Analytics Engine is disabled or the Analytics Read secret is not configured.","sampled":true,"link_ids":null}

成功时两种视图都有 available:true,sampled:true,timezone:"UTC",days,link_ids,clicks,timeline。timeline 为 [{date,clicks}]，没有事件的日期不保证补零；clicks 是成功业务 GET 的采样加权值，不是人数。

full 另外包含：

字段 内容
top 最多 50 条 {link_id,hostname,slug,clicks}
countries / referrers 各最多 20 项 {country,clicks} / {referrer,clicks}，来源仅主机
timezones / ip_timezones {timezone,clicks}，分别是浏览器自报 / IP 地理时区，缺失为 none
devices {device,clicks}，device 为 mobile/pc/none
suspected_vpn_visits / suspected_vpn_successes 疑似事件与其中成功访问估计
blocked_vpn_visits / unknown_timezone_blocks 疑似 VPN 拒绝 / 未知时区拒绝估计
unverifiable_blocks ASN、时区或延迟不可验证的拒绝估计，含未知时区拒绝
unknown_timezone_successes / tor_visits 未知时区成功 / Tor 事件估计
vpn_scope terminal_successes_and_policy_denials_not_unique_users
success_scope authorized_get_redirect_or_text
dimension_sources 如下来源说明 
{"dimension_sources":{"timezone":"javascript_client_reported","ip_timezone":"cloudflare_ip_geolocation","device":"cloudflare_generated_header","browser_timezone":"javascript_client_reported_untrusted","tor":"cloudflare_request_cf_country_T1","device_header_enabled":false}}

整组请求 10 秒上游时限，完整视图最多两路并发；成功结果可在同实例复用 15 秒，权限和链接选择仍每次检查。上游结构/计数失败 502 analytics_query_failed，超时 504 analytics_timeout，调用方取消 408 request_aborted 并停止后续查询。

GET /stats/archive：查 D1 每日归档#

需 analytics:read。支持两种分页和相同 link_id/link_ids，不实现 days 筛选。按 date 降序、link_id 升序。page 响应含 items/page/limit，cursor 含 items/limit/next_cursor；都包含 sampled:true,link_ids,dimension_detail_available:false，都没有 total。

items 为 DailyStat。只包含已写入 D1 且链接仍存在的每日计数，无国家/时区/设备明细；不是实时统计错误时自动启用的后备。统计关闭后，旧归档仍可读。

GET /users：列出成员#

需 users:write 且交互式，即 Owner。返回按创建时间排序的 User 数组，无分页，无单独用户 GET。

POST /users：登记成员#

Owner 交互式。仅接受 email、display_name、role：

{"email":"editor@example.com","display_name":"内容维护","role":"editor"}

email 必需，最长 254，去首尾空白并转小写；display_name 默认空、最长 100；role 默认 viewer，可为 viewer/editor/admin/owner。新用户启用，不能自行传 enabled、access_sub、id、version。返回 201 User，重复邮箱 409，非法角色 400。不会发邮件或修改 Access 策略。

PATCH /users/{id}：修改角色或停用#

Owner 交互式。仅接受 version、display_name、role、enabled：

{"version":1,"role":"viewer","enabled":false}

返回 User，不存在 404、版本旧 409；不能停用/降级最后一名启用 Owner，否则 409 last_owner。不能改邮箱或身份 subject，无 DELETE 用户接口。停用阻止后续身份/令牌认证，不删除其公开链接。

GET /tokens：列出我的令牌#

任意交互式会话，只列本人，按创建时间降序；包括已撤销记录，无分页。scopes 是 JSON 字符串，需 JSON.parse；prefix 只供显示，不是可用 token。不返回完整值、token_hash 或最后使用时间。

POST /tokens：创建我的令牌#

交互式会话。只接受 name、scopes、expires_at。name 为 1–100 字符且非全空白；scopes 原数组 1–5 项，限定为当前用户能授予的五种应用权限，合法重复项去重；越权为 403 invalid_scopes。

expires_at 是创建时起至少 60 秒、最多 365 天的 Unix 秒。使用动态计算，例如 Math.floor(Date.now()/1000)+7*86400，不要复制已经过期的固定时间。50 条未撤销记录后返回 409 token_limit，过期未撤销也计入。这个计数检查不是并发情况下的严格全局配额。

成功 201 返回 id,token,name,scopes,expires_at,shown_once:true；scopes 此时是数组。完整 token 只返回一次，立刻安全保存；读取列表找不回来。

DELETE /tokens/{id}：撤销我的令牌#

交互式且属于本人，无 version、无正文。成功 {"revoked":true}。已撤销、不存在或属于别人均为 404，重复调用不保证再次成功。应用 token 不能调用此接口撤销自己。

GET /audit：查看操作记录#

需 audit:read，即真人 Admin/Owner。支持两种分页，按 created_at DESC,id DESC；cursor 省去总数查询，page 仍有精确 total。没有用户、动作或日期筛选参数。items 为 Audit，details 是 JSON 字符串；敏感内容不会据此恢复。

GET /settings：读取站点设置#

需 settings:write 且交互式，即 Owner。返回按 key 排序的 Setting 数组，可能含归档内部记录。不要把全部读取结果原样提交回去。

PATCH /settings：改站点名称#

Owner 交互式，只接受 site_name，1–80 字符且非全空白：

{"site_name":"团队短链接"}

成功返回同样的 site_name 对象。无 version，最后一次写入生效。此接口不修改 Access、域名绑定、统计开关、KV 或 secrets。

GET /system/health：检查 D1#

需 settings:write，当前实际用户为 Owner。执行 D1 SELECT 1 后返回：

{"worker":"ok","database":"ok","analytics":"configured_not_probed","version":"1.0.2"}

统计配置不完整时为 disabled_or_incomplete。configured_not_probed 只表示配置存在，没有实际查询 Analytics Engine。D1 故障不会返回这份成功对象。

没有列出的 PUT、用户删除、所有权转移、token 刷新、手工归档、API 批量导出等接口，不应假设存在。

4. 访客短链协议#

这些路径位于 Redirect 的短链域名，不带 /Linro/v1。应用 token 不能充当访客解锁密码。

路由和缓存#

方法与路径 用途
GET/HEAD / 200 品牌文本，不列链接或转后台
GET/HEAD /health 裸 JSON {"status":"ok","version":"1.0.2"}，不查 D1
GET/HEAD /robots.txt 禁止索引的文本提示，不是访问控制
GET/HEAD /__Linro_assets/{file} 带指纹的 CSS/JS 可缓存一年，无指纹旧路径 no-store
GET/HEAD /{slug} 跳转、文本、保护页或拒绝
POST /__Linro_unlock/{slug} 密码解锁
POST /__Linro_browser/{slug} 浏览器证明提交
GET /__Linro_rtt（WebSocket Upgrade） 一次连接，五轮服务端 RTT 挑战，成功升级返回 101

内部 POST 路径用错方法返回 405 Allow: POST；其他公开路径只接受 GET/HEAD。公开限流先于 health、资源和业务读取，因此生产限流绑定故障也可能让 health 为 503。

普通有效链接返回配置的 301/302/307/308 和 Location；文本为 200 text/plain; charset=utf-8，没有 Location。不存在或停用为 404；过期按配置为 404/410；次数耗尽为 403。

业务跳转和文本响应禁用 CDN 缓存；前述带指纹静态资源仍可公开缓存。无密码/地区规则/次数上限/浏览器流程的普通跳转，才按 cache_ttl 允许私有客户端缓存，并受剩余有效期约束；文本和保护响应 no-store。不要用外层 Cache Everything 覆盖这些规则。

最终获准的 HEAD 也会消耗有限次数额度，只是没有响应正文，也不记成功点击。密码页 HEAD 不解锁、不扣额度。仅全局采集开启时 HEAD 可直接响应；单链 VPN 检查缺证明时 HEAD 拒绝。

密码提交#

尚未解锁的 GET 返回 200 密码页。POST 正文为 application/x-www-form-urlencoded，只有一个 password 字段，最多 8192 字节。密码错误为 401 HTML。

来源需能证明同源：存在 Sec-Fetch-Site 时必须是 same-origin；显式 Origin 必须与完整 origin 一致。缺失或 null Origin 仅在 Sec-Fetch-Site 明确 same-origin 时可能通过，显式其他 Origin 仍被拒绝。

内置页面用 Accept: application/json 获取 200 JSON，随后普通导航到同源短码；普通表单得到 303。成功设置 __Host-Linro_unlock_* Cookie，最长 900 秒，生产使用 Secure、HttpOnly、Path=/、SameSite=Lax，绑定链接、主机和规则修订。POST 不扣额度、不记成功点击；新的 GET 会再检查规则，密码不发送给目标。

无密码链接的解锁 POST 为 405。修改受保护规则、更换或移除密码可使旧 Cookie 失效。

浏览器检查提交#

全局采集需要 BROWSER_TIMEZONE_ENABLED=true、统计开启和实际 Analytics 写入绑定；单链 block_vpn=1 则独立要求检查。浏览器报告的时区不可信，与平台 IP 时区只是不同来源的信号。

POST /__Linro_browser/{slug} 使用 application/x-www-form-urlencoded 表单，含唯一的 challenge 和 timezone。开启 block_vpn 时，latency 只传 Worker 签发的不透明回执，最长 128 字符。表单最多 4096 字节，挑战最长 2200 字符，时区最长 64 字符。

Accept 只控制成功结果，不改变正文或认证：明确接受 application/json 且 q 有效大于 0 时返回 200：

{"ok":true,"data":{"next":"/welcome?_Linro_check=1"}}

未明确接受 JSON、仅通配或 JSON q=0 时返回 303，Location 为同一个 next。两种成功都设置短期 __Host-Linro_browser_* Cookie、Vary: Accept 和 no-store，不扣额度或记成功点击，也不在 POST 中给出最终目标。

恢复 GET 必须同时有恰好一个 _Linro_check=1 和有效 Cookie。证明最长 120 秒，不延长挑战窗口，绑定规则、主机、查询和网络上下文；缺一、过期或变化都不能绕过。最终会清除 Cookie，但没有服务端一次性消费表，不是绝对防重放的一次性凭据。

单链 VPN 检查先于密码页检查 Tor 和 ASN，仅允许 Radar 的 ACCESS_ISP 与 ORGANIZATION。被提前拒绝时不建立测量连接。

浏览器以相同查询串向 /__Linro_rtt 发起同源 WebSocket GET 升级，子协议列表依次为 linro-rtt-v3、当前签名挑战。Worker 校验来源与挑战后选定第一个子协议。普通 GET 返回 426，旧 POST 返回 405。浏览器发 ready 后开始计时，握手时间不计入样本。Worker 在一条同源 WebSocket 上发出 5 轮随机挑战，浏览器逐条原样回传。每次收到正确回包后等待 400 ms 再发下一轮。Worker 计时并与该连接的 TCP 或 QUIC RTT 比较。五轮全部完成且至少一轮的绝对差严格小于 55 ms 才通过；恰好 55 ms 不算通过。 会话最长 30 秒，且受原挑战到期时间限制。完成时末帧 receipt.<回执> 携带绑定原挑战的认证结果；错误回包、超时或中断无法取得放行凭据。测量不消耗短链次数。

内置 JS 使用普通导航继续，避免把密码/浏览器 POST 链式提交到跨站目标。旧式 303 表单仍在，但不能保证无 JS/Cookie 的客户端完成所有流程。保护页提供中文/English 切换。

公开状态码怎么读？#

状态 常见含义
200 系统路径、资源、保护页、最终文本或内部 POST JSON 成功，须看 Content-Type
301/302/307/308 最终跳转，只证明首跳，不证明目标网页成功
303 内部解锁/检查后的同源继续步骤
400/415 HTTPS、表单或格式不合规
401 密码错误
403 来源不合规、额度耗尽或检查拒绝
404/410 不存在、停用或过期
405 方法错误或不适用的内部 POST
414 请求/组合 URL 过长
429 限流，按 Retry-After 等待
503 数据库、密钥、规则或限流配置故障；不能据此放宽保护
508 最终目标形成直接跳转环路

公开端可能返回 HTML、文本或 JSON，不要对所有响应强行解析管理 API 的 envelope。

5. 从一个只读调用开始#

Bash / curl#

先在秘密管理工具或私有进程环境中设置 Access 服务凭据与 Linro token。下面不会提供真实值，也不自动跟随重定向：

export LINRO_ADMIN_ORIGIN='https://admin.example.com'
: "${CF_ACCESS_CLIENT_ID:?请设置 Access Client ID}"
: "${CF_ACCESS_CLIENT_SECRET:?请设置 Access Client Secret}"
: "${LINRO_API_TOKEN:?请设置 Linro 应用令牌}"

curl --silent --show-error --fail-with-body --max-time 20 \
  -H "CF-Access-Client-Id: $CF_ACCESS_CLIENT_ID" \
  -H "CF-Access-Client-Secret: $CF_ACCESS_CLIENT_SECRET" \
  -H "Authorization: Bearer $LINRO_API_TOKEN" \
  -H 'Accept: application/json' \
  "$LINRO_ADMIN_ORIGIN/Linro/v1/session"

--fail-with-body 对 4xx/5xx 失败；Access 302 仍可能退出 0，要核对 HTTP 状态、Content-Type 和 ok 值。不要加 -L。要列出链接，把末尾改为 /links?pagination=cursor&limit=25，令牌需有 links:read。

创建前先 GET /domains?view=directory 取得真实 domain_id，再把本页创建示例保存为 create-link.json 并改值。下面会真正创建业务记录：

curl --silent --show-error --fail-with-body --max-time 20 \
  -X POST -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -H "CF-Access-Client-Id: $CF_ACCESS_CLIENT_ID" \
  -H "CF-Access-Client-Secret: $CF_ACCESS_CLIENT_SECRET" \
  -H "Authorization: Bearer $LINRO_API_TOKEN" \
  --data-binary @create-link.json \
  "$LINRO_ADMIN_ORIGIN/Linro/v1/links"

创建超时不代表没有写入；先按短码检查结果，再决定重试。不要无条件重放写请求。

PowerShell：读取，再用当前版本改标题#

在私有环境注入相同三项凭据，替换管理主机和链接 ID。此例会修改标题：

$ErrorActionPreference = 'Stop'
$LinroOrigin = 'https://admin.example.com'
foreach ($LinroName in 'CF_ACCESS_CLIENT_ID','CF_ACCESS_CLIENT_SECRET','LINRO_API_TOKEN') {
    if (-not [Environment]::GetEnvironmentVariable($LinroName)) {
        throw "缺少环境变量：$LinroName"
    }
}
$LinroHeaders = @{
    'CF-Access-Client-Id' = $env:CF_ACCESS_CLIENT_ID
    'CF-Access-Client-Secret' = $env:CF_ACCESS_CLIENT_SECRET
    'Authorization' = "Bearer $($env:LINRO_API_TOKEN)"
    'Accept' = 'application/json'
}
$LinroId = '22222222-2222-4222-8222-222222222222'
$LinroUri = "$LinroOrigin/Linro/v1/links/$LinroId"
$LinroCurrent = Invoke-RestMethod -Uri $LinroUri -Headers $LinroHeaders -Method Get `
    -MaximumRedirection 0 -TimeoutSec 20
if ($LinroCurrent.ok -ne $true -or -not $LinroCurrent.data.version) {
    throw '没有收到有效链接对象'
}
$LinroBody = @{version=$LinroCurrent.data.version;title='更新后的标题'} | ConvertTo-Json -Compress
$LinroUpdated = Invoke-RestMethod -Uri $LinroUri -Headers $LinroHeaders -Method Patch `
    -ContentType 'application/json; charset=utf-8' `
    -Body ([Text.Encoding]::UTF8.GetBytes($LinroBody)) `
    -MaximumRedirection 0 -TimeoutSec 20
$LinroUpdated.data | Select-Object id,slug,title,version

读取与修改之间仍可能被别人先修改，409 是正常保护，不要忽略。脚本和诊断输出按私有业务资料保管。

在自己的管理页面调用交互式接口#

真人会话写请求用当前同源 Cookie，不带应用 token，并设置 X-Linro-CSRF: 1。以下函数只演示请求结构，不会自行执行修改：

async function updateSiteName(siteName) {
  const response = await fetch('/Linro/v1/settings', {
    method: 'PATCH',
    credentials: 'same-origin',
    redirect: 'manual',
    headers: {
      'Accept': 'application/json',
      'Content-Type': 'application/json',
      'X-Linro-CSRF': '1'
    },
    body: JSON.stringify({ site_name: siteName }),
    signal: AbortSignal.timeout(20000)
  });
  if (!(response.headers.get('content-type') || '').includes('application/json')) {
    throw new Error('没有收到 JSON，请检查 Access 会话与同源页面');
  }
  const result = await response.json();
  if (!response.ok || result.ok !== true) {
    throw new Error(result.error?.code || `HTTP ${response.status}`);
  }
  return result.data;
}

只在你管理的同源页面中调用，且此接口需要 Owner。不要在不可信网站粘贴携带凭据的脚本，也不要打印认证 Cookie。

6. 主要管理错误码#

先判断认证和 HTTP 状态，再看 code。表中没有的错误也应按失败处理；公开表单错误不必使用同一 JSON 格式。

HTTP code 怎样处理
400 empty_body, invalid_json, unknown_field, invalid_field 检查 UTF-8 JSON 对象、已声明字段、数字/长度/版本
400 invalid_slug, invalid_url, invalid_hostname, invalid_email 按字段约束改输入
400 invalid_code, invalid_query_mode, unsafe_query_mode 使用支持值；敏感目标只能 discard
400 internal_target, private_target, redirect_chain 改成允许的最终目标，不绕过管理/私网规则
400 domain_not_found, admin_hostname 选择已有业务域名，管理主机不能用于短链
400 invalid_geo_rules, duplicate_geo_rule 核对规则结构、数量、代码与重复项
400 invalid_response_mode, invalid_text_content, text_geo_conflict 核对文本长度、模式和空地区规则
400 invalid_block_vpn, invalid_link_password 核对保护字段和密码限制
400 invalid_status, search_too_long, invalid_view 核对列表筛选、UTF-8 模式字节数及视图
400 invalid_pagination, invalid_cursor 不混用 page/cursor，原样传回合法游标

Linro v1.0.2 安全与隐私说明#

English · README · 部署指南 · API

把安全理解为几把不同的锁，会更容易配置：Access 决定谁能进后台，角色决定进来后能做什么，访客密码只决定公开短链是否放行。一把锁不能代替另一把锁。

后台：先验身份，再验权限#

生产后台要求 HTTPS、正确管理主机，以及签名、issuer、audience 和时间都有效的 Access JWT。静态后台也先经过 Worker 鉴权。真人写请求还要求同源和 X-Linro-CSRF: 1；API 拒绝显式不匹配的 Origin。

脚本必须同时通过 Access 并提供 Linro 应用令牌。令牌权限不超过当前用户角色，不能调用用户、设置或令牌管理等交互式专用操作。所有应用令牌只允许修改所属用户创建的链接；读取仍按工作区共享。停用用户、撤销或到期会阻止令牌认证。

这不是多租户隔离：Viewer 也能读取团队目标、说明和纯文本。公开密码不会隐藏后台已授权可读的内容。不要把工作区当作成员互相保密的密码库。

生产配置需通过 preflight，保持全部限流绑定。当前 Admin 只有在 AUTH_LIMITER 存在时才调用预认证限流器，手工移除它不会自动让所有请求失败；不要据此省略必需配置。写限流和其他检查还有各自独立的行为。

公开短链：以当前数据库规则为准#

D1 决定链接现在能否放行。KV 只缓存有限路由信息，不存密码校验串、纯文本正文、计数或根密钥；命中仍须 D1 核验，D1 失败不会依赖旧缓存授权。

目标只接受有效 HTTP(S) 地址，拒绝 URL 内的用户名/密码，默认阻止私有、本地、后台和已管理短链目标。检查不解析 DNS，因此不是完整 DNS 重绑定防御。对私有目标的例外必须逐项审阅。

密码使用随机盐、PBKDF2-SHA256 和独立根密钥参与的 HMAC pepper，数据库不存明文。两个 Worker 必须保留相同的 LINK_PASSWORD_SECRET。解锁只回到同源短链，密码不会被 POST 给目标网站；密码 Cookie 最长 900 秒，规则变更可让旧证明失效。

次数上限是服务端授权次数，符合条件的 HEAD 也会使用额度，不代表独立访客数。数据库提交后若响应丢失，可能保守占用一次，不自动退款。访客电脑已经缓存的跳转也不能由服务器强制收回。

浏览器检查：有局限的信号#

浏览器时区由客户端自己报告，不能当作可信身份。IP 时区和 Tor 标记来自平台，但仍可能存在地理数据误差。单链 block_vpn 还要求 Radar 将 ASN 分类为 ACCESS_ISP 或 ORGANIZATION，并校验同源 WebSocket 五轮服务端测量的加密回执。客户端只回显随机挑战，无法通过填写耗时获得放行凭据；时区、分类或延迟不可验证时会拒绝。

这可能拦住正常旅行用户、校园/企业网络或繁忙设备，也不能保证发现所有代理。只在明确接受这些代价的链接上启用。

挑战与证明有效窗口最长 120 秒，并绑定规则、主机、查询和网络上下文。完成后 Cookie 会清除，但没有服务端一次性消费表；不能宣称绝对防重放。公开密码表单允许的缺失/null Origin 窄例外要求明确同源元数据，显式其他 Origin 仍拒绝，且不会放宽后台 CSRF。

哪些访问数据会被记录？#

位置 可能含什么
D1 成员邮箱、业务链接、文本、密码校验串、令牌哈希和操作审计
GUI JSON/CSV 导出 链接目标、说明、文本及公开配置；不含密码或校验串
Analytics Engine（可选） 链接 ID、主机、短码、国家、来源主机、时区/设备分类、成功或策略拒绝计数

Analytics 事件省略原始 IP、完整 User-Agent、Cookie、挑战、密码、目标和文本。审计对 URL 查询/片段脱敏，正文只记长度，密码只记保护状态。这些措施不代表业务数据变成公开资料，也不代表全部平台日志由 Linro 管理。

限流不是全球精确配额#

Worker 限流按代码指定的 key 和 Cloudflare 位置计数。密码桶用 IP 的 SHA-256 哈希，默认每个 key、每个位置 5 次/60 秒；共享出口可能共用桶，跨位置不是单一原子计数。多个实例应使用独立 namespace。

额外 WAF 规则需按账户支持能力配置。它可以帮助减少尝试，但不能代替身份、来源和数据校验。Cloudflare 限流说明

Linro v1.0.2：检查旧数据，再决定是否清理#

English · 备份与升级

审计、每日统计和已撤销令牌像不断增加的旧收据。Linro 默认保留这些记录，不会自动按日期删除。retention 工具先帮你数一数有多少旧记录；你决定保留多久，工具不会替你执行云端删除。

1. 准备一份私有快照#

工具读取的是本地 SQLite 二进制数据库，不是 D1 导出的 SQL 文本。先按指南导出完整备份，再把可信 SQL 恢复到一个新建、隔离的本地 SQLite 文件。

例如，在自己的私有备份目录中启动 sqlite3 review.sqlite，依次输入 .read Linro-backup.sql、PRAGMA quick_check;、.quit。这需要本机已安装 SQLite 命令行工具。不要用待审查脚本覆盖唯一备份，也不要把真实数据库放进源码目录。

快照可能包含真实邮箱、链接、令牌校验值和审计详情，必须像原始备份一样保护。下面的 SNAPSHOT.sqlite 只是占位文件名，改为你自己的私有快照路径。

2. 先看报告，不改数据#

在项目根目录、Node.js ≥22.16.0 环境运行：

node scripts/retention.mjs --database "SNAPSHOT.sqlite"
node scripts/retention.mjs --database "SNAPSHOT.sqlite" --audit-days 180 --archive-days 365 --revoked-token-days 90 --limit 100

第一条只查看容量。第二条示范“审计保留 180 天、每日统计保留 365 天、撤销令牌保留 90 天”，这些天数不是项目推荐的统一政策，应按自己的需求决定。

选项 根据哪个日期判断旧记录
--audit-days audit_logs.created_at：审计产生时间
--archive-days daily_stats.date：访问所属的 UTC 日期
--revoked-token-days api_tokens.revoked_at：撤销时间；没有撤销的令牌都保留，已到期也一样

省略某个天数就保留那张表的全部记录，策略值显示为 null。工具默认以当前 UTC 日期零点为基准，减去指定天数，只选择严格早于截止时间的记录；恰好在边界上的保留。可以用 --as-of YYYY-MM-DD 固定核对日期，实际运行时换成有效日期。天数为 0 仍保留参考日及之后的记录。

报告输出 JSON，包含总行数、符合条件的行数、下一批行数和大小。总文件占用与可复用空闲页是不同指标：删行后 SQLite 可以复用空间，文件未必立刻缩小。系统没有 dbstat 时，单表字节数为 null，不表示表为空。

3. 需要时，只生成一小批 SQL#

node scripts/retention.mjs --emit-cleanup-sql audit_logs --audit-days 180 --limit 100

这个模式只输出一条 SQL，不打开数据库，也不会执行它。可选表是 audit_logs、daily_stats、api_tokens；每次只能选一张，并给出对应保留天数。默认每批最多 100 行，允许 1–1,000 行。

先固定与报告相同的参考日期，审阅生成 SQL，并在一次性恢复副本中试运行，再重新查看报告。若决定操作正式库，先确认数据库 ID 和可恢复的最新备份，再由有权限的维护者执行已审阅语句。

每次语句只删除一批，重复执行会继续删除下一批。行数上限限制删除量，不保证寻找候选行只读同样少的行。每日统计如果仍在归档补算窗口内，删除后可能又被补写，因此不要把极短保留期当成彻底停止归档的方法；不需要归档时应关闭相应功能。

页面资源与访客流程#

页面使用带内容指纹的 password.css、password.js、browser.js，路径位于 /__Linro_assets/，指纹版本可长期缓存。没有指纹的旧路径继续返回当前资源，但使用 Cache-Control: no-store。

密码和浏览器验证成功时，内置页面接收 200 JSON 并重新打开同源短链；普通表单可得到 303。两种方式都不会把 POST 密码提交给最终目标。完整字段、Cookie 与错误行为见 API。

单链 VPN 检查会先判断 Tor 和 ASN，仅 Radar 的 ACCESS_ISP 或 ORGANIZATION 分类可继续；通过后，Worker 在一条同源 WebSocket 上发出 5 轮随机挑战，浏览器逐条原样回传。每次收到正确回包后等待 400 ms 再发下一轮。Worker 计时并与该连接的 TCP 或 QUIC RTT 比较。五轮全部完成且至少一轮的绝对差严格小于 55 ms 才通过；恰好 55 ms 不算通过。若网络在挑战前就被拒绝，浏览器直接得到 403 结果页，不发送探针。

从 v1.0.1 升级要保留什么？#

保留 Worker 名称、数据库与其他资源绑定、Access 设置和原根密钥。已有令牌哈希、Cookie 名称、KV 键和 CSV 标记保持兼容，已有密码和有效令牌按原期限与规则继续验证。旧的客户端计时回执和 VPN 通行 Cookie 无效，需重新打开短链。某些内部兼容字符串保留旧名称是为了继续读取已有数据，不能只为“看起来统一”而替换。

源码包含 0001_initial.sql 至 0006_destination_hosts_and_archive.sql。已经全部应用六项的数据库无需新增迁移；其他实例按实际迁移账本补齐，不按文件夹版本猜测，也不清库重建。

公开端保留 health、cdn-cgi 和 __Linro_ 前缀，保留判断忽略大小写。Linro 仍可作为普通业务短码；robots.txt 等带点路径不符合短码语法。

Linro#

Your own short links, on your own domains, with a Chinese and English dashboard.

Current release: v1.0.2 · 简体中文

A short link is a small signpost: https://go.example.com/welcome points visitors to a longer address. Linro lets you create that signpost, change its destination, and decide who can use it. It runs in your Cloudflare account; you do not maintain a traditional server.

example.com, example.org, and the other example addresses in this repository are placeholders. They do not identify the project's operator or a working deployment.

What can it do?#

  • Manage up to 50 public short-link domains from one dashboard.
  • Create readable short codes, or let Linro generate one.
  • Redirect visitors with 301, 302, 307, or 308; alternatively, show a small plain-text message.
  • Add a password, an expiry time, an enable/disable switch, or a limit on authorized requests.
  • Choose different destinations by country or continent.
  • Import and export JSON/CSV, manage team roles, and review changes in an audit log.
  • Add optional Analytics Engine statistics, KV route caching, and browser checks when you need them.

The dashboard is a shared team workspace. A Viewer can read the team's destinations and plain-text content. A password on a public short link does not hide its content from authorized dashboard members. See security boundaries.

Linro v1.0.2: from first try to a running service#

简体中文 · README · API reference

This guide starts with a safe local tryout, then walks through production setup. Run commands from the project folder containing package.json, unless a step says otherwise. Do one step, check its result, then continue.

All domains, email addresses, IDs, and paths shown as examples are fictional or explicit placeholders. Replace them in your private configuration. Never publish the filled-in copy.

1. Understand the four main pieces#

A short link works like a signpost: a visitor reads a short address, and Linro tells the browser where to go next.

Name Plain-language meaning In this project
Worker A small program Cloudflare runs for a request One Admin Worker and one Redirect Worker
D1 The shared database, like the office notebook Links, rules, users, settings, and audit records
Access The login gate before the staff area Protects the entire admin hostname
Binding A named connection between a Worker and a resource Both Workers use DB for the same D1 database
Migration A numbered change to database tables Files 0001 through 0006 in migrations/
Secret A private value stored separately from public configuration Password roots and optional API credentials
Slug The short code after a domain welcome in https://go.example.com/welcome

The public Redirect Worker and private Admin Worker have different hostnames. Do not put public short-link hosts behind the admin Access application. KV caching and Analytics Engine are optional; start without them if you only need basic links.

This guide covers application v1.0.2. Its API remains /Linro/v1, and existing application credentials remain valid. Protocol identifiers explains the intentional older compatibility labels.

2. Try the real application on your computer#

For an interface-only practice room, use the static demo. The steps here run the actual Workers locally, with a separate local database.

2.1 Install the tools and dependencies#

Install Node.js 22.16.0 or newer and npm. Extract the complete source ZIP and enter its folder. Check the versions:

node --version
npm --version
node -p "require('./package.json').name + ' ' + require('./package.json').version"
npm ci

The project should report linro 1.0.2. npm ci installs exactly the dependency tree in package-lock.json; keep that lockfile. The project pins Wrangler 4.132.0. To see the resolved Wrangler/Miniflare/workerd toolchain, run npm run toolchain:versions.

If your system has sha256sum, you can check an untouched source release with sha256sum -c MANIFEST.sha256 from its root. After your own edits, original manifest differences are expected; release packaging creates a new manifest.

2.2 Prepare the local database and dashboard#

npm run local:init
npm run build:web
npm run db:migrate:local
npm run db:seed:local

local:init prints a local development token. Keep it private and enter it when the local dashboard asks. It creates .local/ settings, preserves valid existing local secrets, and does not erase existing local database state. Local data stays in .local/state; both local Workers share it. None of these steps migrates your cloud D1 database.

2.3 Start the two local services#

In the first terminal:

npm run dev:admin

In a second terminal, in the same project folder:

npm run dev:redirect

Open the local dashboard. The public local endpoint is http://127.0.0.1:8788. The seed step creates its local domain record. Create a link with destination https://example.org/, use status 302 and browser cache 0, then open the short address.

Stop each process with Ctrl+C. To try the local KV path, run npm run local:init -- --kv and restart the local services. Keep .local/ out of Git and public archives. Its development token is not a production login mechanism.

Local testing can check forms and database behavior. It does not reproduce Cloudflare's real visitor country, ASN, connection RTT, Access policies, DNS, TLS, or distributed rate limiting.

3. Prepare your Cloudflare resources#

You need a Cloudflare account, permission to create resources in it, and domains you control. An example layout is:

Address Purpose
admin.example.com Private dashboard and admin API
go.example.com Public short links

Replace these with your own hostnames. Use an active Cloudflare zone that can host Worker Custom Domains. Existing conflicting DNS records, including a CNAME on the chosen hostname, need review before a Custom Domain can be added. See Custom Domains.

3.1 Sign in to the correct deployment account#

npx wrangler --version
npx wrangler login
npx wrangler whoami

Wrangler login authorizes your terminal to manage Cloudflare resources. It is separate from the Access login your dashboard users will use.

Confirm the Account ID. Account ID, Zone ID, D1 database ID, and Access audience are different values. If you have several accounts, set the intended account before resource creation. In Bash:

read -r -p "Target Cloudflare Account ID: " CLOUDFLARE_ACCOUNT_ID
export CLOUDFLARE_ACCOUNT_ID

In PowerShell:

$env:CLOUDFLARE_ACCOUNT_ID = Read-Host 'Target Cloudflare Account ID'

3.2 Create one shared D1 database#

For a new installation:

npx wrangler d1 list
npx wrangler d1 create linro
npx wrangler d1 info linro

Record the returned database name and UUID. Both Workers must use this same database. If Wrangler offers to rewrite one configuration automatically, leave that change to the project's configuration generator so both sides stay consistent.

For an existing installation, reuse its database and follow Backup and upgrade. Do not create a replacement database merely to update the code, and do not upload the local development database to establish a production Owner.

3.3 Put Access in front of the whole admin host#

In Cloudflare Zero Trust, create a self-hosted public application for the admin hostname. The exact dashboard labels can change; the required settings are:

Setting What to choose
Hostname Your admin hostname
Path Leave blank, so the entire hostname is protected
Human policy Allow specific approved email addresses or an identity group you control
Login method The email OTP or identity provider configured in your account
Public short-link hosts Keep them outside this admin application and check overlapping wildcard applications

Keep the gate restrictive. Do not add a Bypass policy or an unrestricted Everyone rule to make setup easier. The Worker checks the Access JWT again after the outer gate.

Record the application's issuer and Audience (AUD), and choose the first Owner's Access email. The issuer has the shape https://YOUR-TEAM.cloudflareaccess.com, without a trailing slash. The audience is not the application ID and not an API token.

Official instructions: self-hosted public applications. Cloudflare deployment permissions do not automatically grant permission to administer Access.

4. Configure, migrate, and deploy#

There are three places for settings. Keep them separate:

Place What belongs there
Private deployment.json Resource IDs, hostnames, Access settings, feature switches
Worker secrets Private root secrets and optional service API credentials
Linro dashboard / D1 Links, domain records, users, and the displayed site name

4.1 Copy the public example once#

In Bash:

test ! -e deployment.json && cp deployment.example.json deployment.json

In PowerShell:

if (Test-Path .\deployment.json) { throw 'Review the existing file instead of overwriting it.' }
Copy-Item .\deployment.example.json .\deployment.json

Edit the new file with your own values. Fill the account, database, admin host, public hosts, Access issuer/AUD, and Owner email. Keep the optional switches off initially:

{
  "analytics_enabled": false,
  "browser_timezone_enabled": false,
  "cloudflare_device_type_enabled": false,
  "redirect_cache_namespace_id": ""
}

This small JSON is a fragment to explain those switches, not a complete deployment file. Keep the required fields from deployment.example.json. Set source_url to the published source matching the code you will run; see Licensing. The public example leaves it empty so it cannot imply a real source publication.

Generate and check the two Worker configurations:

npm run configure -- --config deployment.json
npm run preflight

configure overwrites apps/admin/wrangler.jsonc and apps/redirect/wrangler.jsonc. Review their Worker names, account/D1 IDs, hostnames, bindings, and switches before deployment. It does not create D1, Access applications, dashboard domain records, or secrets. preflight checks local configuration; it cannot prove remote secrets, DNS, certificates, or tables work.

Keep these generated safety settings: workers_dev: false, preview_urls: false, and Admin assets.run_worker_first: true. The Admin Worker also explicitly enables enable_request_signal with compatibility date 2026-09-15. This allows a disconnected statistics request to cancel outstanding provider requests. Preserve the flag; SQL already accepted by the provider can still complete. Cloudflare compatibility flags

npm run check

npm run test:runtime
npm run build
npm run test:browser
npm run deploy:dry-run

The regular tests, native workerd tests, and real browser tests cover different behavior. The command does not run remote migrations or browser tests. Complete those steps separately. The two Workers are not deployed atomically.

4.5 Sign in and create a first link#

Open your admin hostname and sign in through Access with the configured Owner email. Linro creates the first Owner only when the users table is empty. Changing owner_email later does not replace an existing Owner.

In Domains, add the public hostname already bound to the Redirect Worker. Then create a test link with slug install-check, a normal public target, status 302, query mode discard, and browser cache 0. Check:

npm run verify:deployment
curl -sS -D - -o /dev/null https://go.example.com/install-check
curl -sS https://go.example.com/health

Replace the hostname first. On Windows use curl.exe and -o NUL. Do not add -L: inspecting the first response tells you what Linro returned without following the destination. The test link should have the expected status and Location. Public /health reports status: "ok" and version: "1.0.2"; it does not query D1.

Also check that an unauthenticated admin visit meets the Access gate. The Owner's Settings → health check queries D1; its analytics field reports configuration only. Test each optional protection on dedicated records before enabling it on important links.

4.6 Add another public hostname#

A hostname needs two registrations: Cloudflare routes traffic to the Redirect Worker; Linro's D1 domain record tells the application which host it may serve.

  1. Add the hostname to redirect_hosts in private deployment.json.
  2. Run configure, review the complete generated host list, run preflight, and deploy the reviewed change.
  3. Add the same hostname in the dashboard's Domains page.
  4. Create a dedicated test link and verify that hostname's /health and redirect.

The dashboard cannot create DNS or Custom Domains. Conversely, a successful public health response does not prove a D1 domain record exists. Removing a D1 record does not detach Cloudflare routing. Before removing a host, move or delete its links and review both registrations deliberately.

5. Use the dashboard day to day#

5.1 Create and edit links#

Select a registered domain, enter a destination, and choose a slug. An empty slug on creation produces an eight-character random code. The same slug can exist on different domains; within one domain it is unique and case-sensitive. Use 1–64 ASCII letters, numbers, underscores, or hyphens. health, cdn-cgi, and the __Linro_ prefix are reserved, ignoring case; Linro is a valid business slug.

Start with 302 and cache_ttl=0. Browsers can remember permanent redirects such as 301/308; later edits cannot recall a response already stored by a visitor. Domain defaults affect future links that omit their own redirect code, not existing links.

Editing uses a version, like a revision number on a shared document. If someone changes the link after you opened the form, a 409 conflict asks you to reload and compare changes. Do not blindly replay the old form with a new version number.

Bulk enable/disable/delete handles at most ten items per API call and can partially succeed. Read the individual results. Disabled, expired, and exhausted filters can overlap; they are not separate parts that add up to the total.

5.2 Understand destinations and query parameters#

Targets are absolute HTTP(S) URLs. The final normalized URL must fit 4096 characters. Credentials, whitespace/control characters, backslashes, the admin hostname, and managed short-link hostnames are rejected. Private/local targets are denied unless the deployer explicitly allows an exact host. Validation does not fetch a destination or resolve its DNS.

A query is the part after ? in a URL. Forwarding only reviewed keys avoids passing arbitrary visitor data to the destination:

query_mode Result
discard Keep the destination's existing query; ignore incoming visitor query keys
merge Add allowed incoming keys; existing destination values win on a duplicate key
replace Clear the destination query and use only allowed incoming keys, even if none survive filtering

Sensitive sign-in/reset/redirect destinations must use discard. Older unsafe stored combinations are treated as discard on public reads. _Linro_check and _Linro_lang are internal and never forwarded. The final combined destination can be at most 8192 characters.

5.3 Add rules only when needed#

Rule What it means
Expiry Stop serving after a Unix-second timestamp; expired responses use configured 404 or 410
Maximum requests Count final authorized GET and HEAD responses; not unique people
Geographic routing Try country, then continent, then the default target; at most 32 unique rules
Plain text Return a small message with text/plain, never execute it as HTML
Password Require visitor unlock; setup is in the next chapter
VPN policy Apply heuristic network/browser checks; legitimate visitors can be denied

A finite count increases only when the link has a limit. Changing the limit does not reset the count; use the explicit reset operation. Password/check pages and their intermediate responses do not consume the link's finite quota. A lost connection after a committed authorization can still consume one slot.

Plain text accepts 1–16,384 JavaScript string code units and at most 32,768 UTF-8 bytes. It forces query_mode=discard, requires empty geographic rules, and always uses no-store. Password, expiry, disablement, limits, and browser rules still apply.

Capability Viewer Editor Admin Owner
Read team links, targets, text, domains, and analytics Yes Yes Yes Yes
Create links and change own links No Yes Yes Yes
Change other members' links No No Yes Yes
Manage domain records and read audit No No Yes Yes

An Owner adds the member's email and role in Linro and allows that identity in Access. Both steps are needed. First sign-in binds the Access subject; later use of the same email with a different subject does not silently replace it. There is no user-email-change or identity-rebinding API.

The last enabled Owner cannot be disabled or demoted. For a handoff, first create another Owner and verify their login. Disabling a user does not disable their old public links. Linro Owner permissions do not grant Cloudflare account administration.

5.5 Connect an automated client#

Automation needs two keys: Access service credentials for the outer gate, and a Linro token for application permissions. Add an appropriate Service Auth policy to the existing admin Access application and retain the human Allow policies. Creating a service token alone does not grant access to that application. See Access service tokens.

Create a Linro token in the dashboard. Available scopes are links:read, links:write, links:delete, domains:read, and analytics:read, limited by the user's role. Management scopes cannot be granted to tokens. All tokens can write only links created by their owning user, even for an Owner; use a separate user when an integration needs separate ownership.

The token is shown once. Save it privately. Expiry must be 60 seconds to 365 days ahead. Up to 50 non-revoked token records count toward the user's limit; expired-but-unrevoked records still count. Tokens cannot manage other tokens. The API reference explains headers and request examples.

5.6 Import and export#

GUI export reads the entire shared workspace, not just the visible search or selected rows. It retrieves up to 10,000 links, 100 per page, and checks for duplicate/count inconsistencies. It is not a transaction snapshot while other people are editing.

JSON includes format: "linro", version 1.0.2, export time, domain data, site name, and links. Neither JSON nor CSV contains password verifiers or original passwords. CSV keeps the _cf_links_csv escaping marker for compatibility and includes quoting/formula protection; use the project's importer rather than splitting lines on commas.

Import accepts a JSON array, an object with links, or CSV: at most 2 MiB and 1–5,000 rows. YOURLS-style keyword, url, and title are supported. Create domains first; an input hostname is matched to an existing domain, otherwise the selected domain is used.

The GUI validates records, then sends batches of at most ten links and 262,144 JSON bytes. Each batch commits independently. A confirmed pre-write 429 rate_limited is retried once after Retry-After; repeated limiting can resume at the current batch. After a timeout or connection loss, reconcile saved records before retrying because the write may already have committed.

An exported password_protected: true record needs a new password on import. It cannot silently become unprotected. Import creates new links owned by the current user; it does not restore original users, tokens, ownership, counters, audits, or archive history. Link export is not a disaster-recovery backup.

6.2 Password protection#

After storing the password root on both Workers, refresh the dashboard. A link password needs 12–128 JavaScript string code units, at most 512 UTF-8 bytes, and no control characters. It is not trimmed; surrounding spaces are part of it.

In API updates, omit password to keep it, provide a string to replace it, or send null to remove it. Empty text is not a valid password or a universal “keep” command.

A permitted visitor sees the password page. A wrong password returns 401. A correct one sets a 900-second unlock cookie and resumes with a same-origin GET. The password body stays on the short-link site. Store the root secret separately from backups: the database contains a verifier, not recoverable plaintext.

6.3 KV route caching#

Leave redirect_cache_namespace_id empty to use D1 directly. To enable KV, create a namespace:

npx wrangler kv namespace create REDIRECT_CACHE --config apps/redirect/wrangler.jsonc

Put the returned ID in private deployment.json, then regenerate, review, check, and deploy both Worker configurations. Both must bind the same REDIRECT_CACHE. Existing installations should reuse their namespace.

redirect_cache_ttl defaults to 300 seconds. Per-link kv_cache_ttl is null to inherit, 0 to bypass, or 60–86400 to override. This is different from cache_ttl, which controls allowed private browser caching.

Only eligible ordinary redirects use KV. Passwords, active global browser collection, per-link VPN checks, finite limits, expiry, geographic rules, text mode, disabled/missing links, and explicit opt-outs bypass it. A KV hit still requires current D1 authorization. A hot in-instance snapshot can reduce repeated KV access; a cold instance adds KV I/O and revalidation. Therefore KV does not automatically make every workload cheaper or faster.

Refill attempts are suppressed for unchanged versions within a bounded Worker instance for their TTL, including failed attempts. This is not an account-wide write cap. As a simple budgeting example, one continuously active link refreshed every 300 seconds would imply 288 refills/day in a single-refill model; at 3600 seconds, 24. Real edge instances and propagation can add writes. Measure KV operations, D1 rows_read, and latency separately. KV pricing · D1 pricing

6.4 Analytics and daily archives#

Set analytics_enabled: true only when you want event statistics. The Redirect Worker gets the ANALYTICS writer binding; the Admin Worker queries the same account and dataset with a private token granting Account → Account Analytics → Read:

npx wrangler secret put ANALYTICS_API_TOKEN --config apps/admin/wrangler.jsonc

Review the generated configurations and deploy them. To verify only the SQL credential, provide CLOUDFLARE_ACCOUNT_ID and ANALYTICS_API_TOKEN through a private process environment and run:

node scripts/verify-analytics-token.mjs

It runs a bounded read-only SELECT 1, without printing the token. Success does not prove the dataset has events. Do not place the credential in a command argument or tracked file. Analytics Engine SQL API

A successful final business GET records a click; HEAD, password pages, browser pages, and intermediate verification responses do not. Policy rejections have separate counters. Counts are sampled weighted estimates, not unique people. Events omit raw IPs, full user agents, target URLs, text bodies, cookies, and passwords; referrers are reduced to hostnames.

The dashboard uses one AE query. Full statistics use eight queries, at most two concurrently, within a shared ten-second deadline. Completed results may be reused for 15 seconds within one instance; permissions and selected-link existence are still checked. Frequent full-dashboard polling is unnecessary work.

Daily archiving runs only when analytics and analytics_rollup_enabled are both on. Cron defaults to every 15 minutes; supported intervals are 5, 15, 30, 60, 360, and 1440 minutes. It initially archives the two most recent complete UTC days, processes up to 400 link/day groups per batch, saves progress, and catches up from the completed watermark. A completed window is normally rechecked after six hours; unchanged estimates do not rewrite daily rows.

The D1 archive keeps daily click totals, not all live country/timezone/device dimensions. Disabling analytics leaves old archive rows readable. To inspect growth or choose retention periods, see Retention. available:false and a query failure are different from zero clicks.

6.5 Browser timezone collection and VPN checks#

Global collection defaults off. Its effective public flow needs browser_timezone_enabled: true, Analytics enabled, a working writer binding, and a valid browser-check root. An individual link's block_vpn runs independently of the global collection switch.

Global collection Per-link block_vpn Result
Off Off Direct ordinary handling, with other configured protections still active
On Off Collect timezone only when Analytics/writer prerequisites exist; mismatch or unknown does not itself deny access
Off On Still enforce the link's browser/network policy
On On Collect and enforce the link's browser/network policy

Before enabling block_vpn, give Redirect a read-only Radar token with Account → Radar → Read:

npx wrangler secret put RADAR_API_TOKEN --config apps/redirect/wrangler.jsonc

The Worker checks Tor and the visitor ASN before the password page; only ASNs in the Radar categories ACCESS_ISP and ORGANIZATION proceed. Classification lookups have bounded caching, concurrency sharing, and failure cooldowns. The Worker sends five random challenges over one same-origin WebSocket. The browser echoes each one unchanged. After each valid echo the Worker waits 400 ms before starting the next round. It times each round against the TCP or QUIC RTT of that connection. All five must complete and at least one absolute difference must be strictly below 55 ms. Exactly 55 ms does not qualify. Missing/unverifiable RTT also denies it. Radar setup

The browser reports Intl.DateTimeFormat().resolvedOptions().timeZone. The server compares normalized timezone identifiers with request.cf.timezone, not just today's UTC offset. request.cf.country === 'T1' is the Tor signal. Self-reported timezone is untrusted. Travel, system settings, shared networks, device load, and geolocation mistakes can cause false positives. Unknown timezone is not proof of VPN use, but block_vpn rejects it.

A check page leads to a same-origin POST, a short-lived proof cookie, and a fresh GET with current D1 checks. Proof expires within the original 120-second challenge window. There is no server-side one-use consumption table; do not describe it as absolutely replay-proof. JavaScript/cookies are needed for the intended flow. HEAD skips collection-only JavaScript, but a VPN-protected HEAD without valid proof returns 403.

Browser checking adds requests and latency. Use it where its policy is useful, not simply because it is available. A pre-challenge network denial returns a 403 result page and sends no RTT probe.

6.6 Device headers and rate limits#

Device type defaults to none. Turn on cloudflare_device_type_enabled only when your platform configuration reliably generates and overwrites CF-Device-Type. The mapping is mobile/tablet → mobile, desktop → pc, otherwise none. A visitor-supplied header is not trustworthy device detection.

Rate limits use application-defined keys per Cloudflare location, not strict global or daily quotas. Password attempts default to five per hashed-IP key per 60 seconds; shared exits can share a bucket. Keep all four namespaces distinct, including from other installations. A separately reviewed WAF rule for password POSTs can supplement the application limiter, subject to your account's features and cost; the project does not create WAF rules.

7. Back up, upgrade, and recover#

7.1 Keep a recoverable set#

A full recovery set includes matching source and lockfile, D1 SQL export, private deployment/Worker configuration, active version IDs/traffic/bindings/triggers, and root secrets stored separately. A D1 export contains users, business data, token hashes, password verifiers, audits, and D1 archive rows. It does not contain Worker secrets or raw Analytics Engine events. KV is rebuildable cache.

After confirming the account and database, use a fresh private output filename:

npx wrangler d1 export DB --remote --config apps/admin/wrangler.jsonc --output Linro-backup-before-change.sql

npm run backup is a shorter wrapper with the fixed output name Linro-backup.sql; preserve an older backup before using that name again. Export can affect database availability while it runs, so schedule appropriately. Encrypt/protect the backup and practice restoring it. D1 import/export

7.2 Upgrade an existing instance#

Keep the old working copy available. Merge the new source into a separate working directory with your reviewed private settings. Preserve both Worker names, the account and D1 IDs, hostnames, Access settings, optional resource bindings, dataset, and existing root secrets. Do not replace them with public templates.

Check all six migrations against the actual database. If all are already applied, this v1.0.2 patch needs no additional migration. Otherwise back up and apply pending migrations with the normal commands. Re-run checks, build, regular/runtime/browser tests, and dry run. npm run deploy does not create or migrate D1.

For a normal reviewed deployment, use npm run deploy and verify both active Workers. Operators who need a separate upload/review/traffic-switch step can use Wrangler versions:

npx wrangler versions upload --config apps/admin/wrangler.jsonc --keep-vars --tag v1.0.2
npx wrangler versions upload --config apps/redirect/wrangler.jsonc --keep-vars --tag v1.0.2

Record each returned version UUID and compare its resources. --keep-vars is not lossless preservation of every setting; review explicit vars, bindings, assets, and runtime options. Uploading alone does not switch traffic. After review, use the matching IDs:

npx wrangler versions deploy YOUR_REDIRECT_VERSION_UUID@100 --config apps/redirect/wrangler.jsonc
npx wrangler versions deploy YOUR_ADMIN_VERSION_UUID@100 --config apps/admin/wrangler.jsonc

Answer Wrangler's prompts only after checking the target. The two switches are separate. A version-based code update does not by itself reconcile every hostname or Cron change; use the appropriate reviewed deployment workflow when intentionally changing those settings. Do not run trigger synchronization merely as a routine code-upgrade step. Wrangler Worker commands

Afterward, check public HTTPS health on every host, Owner/D1 health, ordinary redirects, roles, and any enabled password/browser/analytics flows. v1.0.1 API paths, token hashes, cookie names, KV keys and CSV markers stay compatible. Reopen the link for a new challenge after the WebSocket update invalidates earlier RTT receipts and VPN proofs.

7.3 Restore or roll back deliberately#

Test SQL backups in a new isolated SQLite file or recovery D1 database before touching production. Validate tables, counts, foreign keys, migrations, rule triggers, and password capability with the matching root secrets. The SQL export may already contain schema and migration records; inspect it before adding a separate initialization step.

A code rollback routes traffic to a prior compatible Worker version. It does not undo database changes or secret rotation. Never overwrite new business data merely to roll back code. A missing password-root secret cannot be reconstructed from stored verifiers; keep secure copies before an incident.

Use the read-only retention report to measure audit/archive/token growth. Generated cleanup SQL is for review and a controlled maintenance action, not an automatic background job.

Linro v1.0.2 API reference#

简体中文 · Setup and usage · Security

An API is the dashboard's set of buttons for programs. A path chooses the button, an HTTP method chooses read/create/change/delete, and a JSON body supplies its fields. This reference describes all 25 admin method/path combinations in v1.0.2, plus the public visitor flow.

Start with authentication and a read-only /session call. Then use the endpoint and field tables for your integration. All example domains, email addresses, UUIDs, and records are fictional. Replace IDs with values returned by your own instance; never use documentation examples as credentials.

1. Make a valid admin request#

1.1 Base address and authentication#

The example base address is:

https://admin.example.com/Linro/v1

All admin paths below are relative to that base. Casing matters. /Linro/v1 itself is not an index, and an extra trailing slash is not automatically normalized. Unknown method/path combinations return 404 api_not_found.

Production authentication has two layers:

  1. Cloudflare Access admits the identity to the admin hostname. The Worker verifies its Access JWT.
  2. Linro checks an enabled user and that user's permissions. An automated client supplies a Linro application token as well as Access service credentials.
Header When to use it
Accept: application/json Recommended for admin requests; an Access login page is still not a successful JSON response
Content-Type: application/json Required when sending an admin JSON body; charset=utf-8 is accepted
CF-Access-Client-Id, CF-Access-Client-Secret A server-side client's Access service credentials
Authorization: Bearer Linro_… The complete Linro token returned when it was created
Cf-Access-Jwt-Assertion Valid JWT supplied after Access authentication; do not invent one
Origin Interactive writes require the exact admin origin; the browser normally supplies it
X-Linro-CSRF: 1 Required for interactive Access writes, not reads
X-Linro-Dev Restricted local loopback development only

Interactive Access writes also reject Sec-Fetch-Site: cross-site. Explicit bearer/local-development credentials use a different CSRF path, but every admin API request rejects a supplied Origin that differs from ADMIN_ORIGIN, including empty or literal null values. A server-side client can omit Origin.

The API does not provide permissive cross-origin CORS, a public OPTIONS preflight contract, or JSONP. Keep automation credentials on a trusted server. A malformed Authorization header selects the token branch and fails; it does not fall back to the browser's human login. Interactive-only routes therefore need the ordinary signed-in session without an application token attached.

1.2 Responses and errors#

A successful response wraps the endpoint result in data:

{"ok":true,"data":{"deleted":true}}

An error uses this shape:

{"ok":false,"error":{"code":"version_conflict","message":"This item changed. Refresh before saving again.","request_id":"example-request-id"}}

Resource creation/import normally returns 201; other successful admin operations return 200. data may be an object or an array. Branch on HTTP status and error.code, not the English wording of message.

Admin API responses use Cache-Control: no-store. Wrapped responses include X-Request-Id and the Worker's security headers; HTTPS responses include HSTS. Application rate limits return 429 with Retry-After: 60. Access/platform failures handled before Linro can instead be HTML or redirects with no Linro envelope. Check status and Content-Type before parsing JSON.

1.3 Bodies, types, and edit versions#

Admin JSON bodies are limited to 262,144 actual streamed bytes. The root must be a valid UTF-8 object, not an array or null. Undeclared fields in normal top-level write bodies are rejected. Bulk item objects are not a strict unknown-field boundary; send only their documented fields. Use JSON numbers for numeric fields; "302" is different from 302.

Business booleans generally accept true, false, 1, or 0; reset_redirect_count accepts only a boolean. Most length limits count JavaScript UTF-16 code units. Password and text fields also have separate UTF-8 byte limits.

Timestamps such as created_at, updated_at, expires_at, and revoked_at use Unix seconds. Export exported_at is ISO text; archive date is a UTC YYYY-MM-DD string.

Think of version as the revision number on a shared document. Link/domain/user PATCH requires the current positive integer version; link/domain DELETE uses ?version=…. A stale revision returns 409. Settings have no version and use last-write-wins. Token revocation has no version. Public visit counters and rule_revision are separate from the admin edit version.

There is no Idempotency-Key implementation. A timed-out POST may already have committed. Before retrying a write, query its expected business record and reconcile the outcome.

1.4 Pagination#

/links, /audit, and /stats/archive support two modes:

Mode Request Response fields
Page, the default page=1&limit=25 items, page, limit; exact count depends on endpoint
Cursor pagination=cursor&limit=25 items, limit, next_cursor; send that cursor for the next page

page defaults to 1 and is 1–100000; limit defaults to 25 and is 1–100. A supplied cursor is at most 512 code units. Cursor mode must not include page; page mode must not include cursor. An invalid mode/mix returns invalid_pagination, and malformed cursor data returns invalid_cursor. Treat returned cursors as opaque strings and keep the same filters while continuing. A null next_cursor means no further page was found. Lists are not transaction snapshots.

For /links, include_total=true|false controls an exact count in either mode; its default is true for page mode and false for cursor mode. /audit includes total only in page mode. /stats/archive never includes total. Domains/users/tokens/settings return arrays without these paging fields.

4.2 Final responses and finite counts#

A valid redirect returns its 301/302/307/308 and Location. A valid text link returns 200 text/plain; charset=utf-8, with no destination Location. Missing/disabled link or domain returns 404; expired uses configured 404/410; exhausted quota returns 403 without revealing the target.

The Worker checks current link/domain state, protection prerequisites, and remaining quota. For block_vpn, Tor/ASN policy precedes the password/browser flow. Final destination/rule validation and finite-quota authorization happen before serving the business response.

An authorized HEAD consumes one finite slot just like GET, but has no body and records no successful-click event. A HEAD of a password page does not unlock or consume quota. A VPN-protected HEAD without proof returns 403; collection-only HEAD can skip JavaScript.

Ordinary redirects can use cache_ttl for private client caching. Password, geographic, finite-limit, and browser flows use no-store; text always uses no-store. Do not override these with an outer Cache Everything rule. Already-issued cached redirects cannot be recalled.

4.3 Password POST#

A GET without a valid password cookie receives a 200 password page when other policies permit. The form sends exactly one password to the same-origin unlock path using application/x-www-form-urlencoded, with a maximum body of 8192 bytes.

If Sec-Fetch-Site is supplied it must be same-origin. An explicit real Origin must match the full public origin. Missing Origin or literal null is accepted only with explicit Sec-Fetch-Site: same-origin. Contradictory foreign Origin is always rejected. These headers are browser-origin protection, not authentication of arbitrary HTTP clients; the password and current rules still apply.

Wrong password returns 401. Success sets a 900-second production __Host-Linro_unlock_* cookie with Secure, HttpOnly, Path=/, SameSite=Lax, bound to host/link/rule revision. The built-in script requests JSON, receives 200, and starts a fresh same-origin GET. A regular form gets 303 to that same short code. The password body is never forwarded to the destination.

The POST itself consumes no link quota and records no successful click. A link without a password rejects unlock POST with 405. Protected-rule/password changes invalidate cookies issued under the old revision.

4.4 Browser POST and latency probe#

A GET may show the browser page when effective global collection is active or the link has block_vpn. Effective global collection needs both switches and the Redirect Analytics writer. A valid root secret is needed to issue/verify challenges.

The same-origin form sends challenge and timezone once each to /__Linro_browser/{slug}. With block_vpn the latency field contains only the opaque Worker-issued receipt (up to 128 characters). The form is limited to 4096 bytes, the challenge to 2200 characters, and the timezone to 64 characters.

The browser upgrades a same-origin GET at /__Linro_rtt with the original query and offers linro-rtt-v3 followed by the signed page challenge as WebSocket subprotocols. The Worker validates the origin and challenge and selects the first protocol. A plain GET returns 426 and the old POST returns 405. Timing begins after the browser sends ready, excluding the upgrade. The Worker sends five random challenges over one same-origin WebSocket. The browser echoes each one unchanged. After each valid echo the Worker waits 400 ms before starting the next round. It times each round against the TCP or QUIC RTT of that connection. All five must complete and at least one absolute difference must be strictly below 55 ms. Exactly 55 ms does not qualify. The session expires after 30 seconds or when the page challenge expires, whichever comes first. The last frame is receipt.<receipt> and authenticates the outcome for this challenge. Wrong echoes, timeouts and interrupted sessions cannot authorize a link. Measurement itself consumes no quota.

Browser timezone comes from Intl.DateTimeFormat().resolvedOptions().timeZone; IP timezone comes from platform metadata. It is an untrusted client signal, not VPN or identity attestation. With VPN blocking, only ASNs classified as ACCESS_ISP or ORGANIZATION by Radar proceed; a failed RTT check, an unknown timezone or unverifiable data denies access. A pre-challenge denial opens no WebSocket.

The Accept header changes only the success representation, not the form body or authorization:

Accept Success
Explicit application/json with valid q > 0 200 JSON such as {"ok":true,"data":{"next":"/welcome?_Linro_check=1"}}, no Location
Wildcard, absent, or JSON q=0 303 to the same-origin resume path

Both forms set the short-lived proof cookie, no-store, and Vary: Accept; neither consumes quota or records a successful click. The POST never returns the final destination. Built-in JavaScript uses a fresh ordinary navigation so CSP form-action 'self' does not turn the eventual cross-site redirect into a blocked form chain. No-JavaScript completion is not guaranteed.

Challenge/proof lasts at most the original 120-second window and is bound to host, link/revision, query, and network context, including ASN for VPN policy. Resumption requires exactly one _Linro_check=1 plus valid proof. Marker-only or cookie-only requests cannot skip the flow. The final response clears the proof cookie, but there is no server-side single-use consumption table: do not promise absolute replay prevention within a still-valid context.

Chinese/English switching preserves the password field or current check state. A blocked normal browser navigation receives a bilingual 403 result page; protocol clients may receive plain text. Read status and Content-Type rather than assuming all public errors are JSON.

Linro security: what each lock protects#

简体中文 · README · Guide

This page describes v1.0.2. Think of security as several locks with different jobs: a dashboard login lock, permissions inside the dashboard, and optional locks on individual public links.

The dashboard door#

Production requires the correct HTTPS admin origin and a valid Cloudflare Access JWT. The Worker verifies the JWT's signature, issuer, audience, and time limits itself. Keep Access protection on the whole admin hostname, keep workers_dev and preview_urls disabled, and keep assets.run_worker_first: true so dashboard files also pass authentication.

A human must pass Access and be an enabled Linro user. Interactive writes require the exact same origin and X-Linro-CSRF: 1; cross-site browser writes are rejected. The narrow origin exception used by the public password form does not change admin CSRF rules.

An automated client needs both Access credentials and a Linro application token. Its effective permissions are checked against its user's current role on every request. Token writes are restricted to links created by that user, even if the user is an Owner. Two tokens owned by one user share that ownership boundary.

What team members can see#

Linro is a shared workspace. Every authorized reader can see team link targets, descriptions, and plain-text content. Public password protection does not hide those fields from dashboard members. Passwords and stored password verifiers are not returned by the normal GUI, API, or exports.

Editors can change their own links. Interactive Admins and Owners can maintain all links. Owners alone manage users and site settings. Disabling a user blocks later logins and token authentication, but does not automatically disable that user's existing public links. See the role table.

Passwords and browser checks#

A link password is stored as a salted PBKDF2-SHA256 verifier with an HMAC pepper. The separate root secret, LINK_PASSWORD_SECRET, must match on both Workers. Preserve it during upgrades: replacing it affects verification of existing passwords. A successful unlock submits only to the short-link site and returns to the same-origin short code; it does not forward the password body to the destination.

Browser timezone is self-reported and can be changed by the visitor. IP timezone, ASN, and the Tor marker come from Cloudflare metadata. Per-link block_vpn requires Radar to classify the ASN as ACCESS_ISP or ORGANIZATION and requires an authenticated receipt for five server-timed WebSocket rounds. The client echoes random challenges and cannot supply its own duration. Unknown or unverifiable information is denied under that policy. Travel, system settings, corporate networks, campus networks, geolocation mistakes, and network delays can all cause legitimate visitors to be rejected. This is a heuristic access policy, not proof of a person's identity or reliable proof of VPN use.

Challenges and proofs last at most 120 seconds and are bound to the link rules, host, query, and network context. The final response clears the proof cookie. There is no server-side single-consumption table, so the valid context must not be described as absolutely replay-proof. Turning off global timezone collection does not turn off block_vpn on an individual link.

Database, cache, and counters#

D1 decides whether a request is authorized now. KV stores an allowlist of ordinary routing fields; it does not store password verifiers, text bodies, counters, or root secrets. Every cache hit still needs a D1 guard. If D1 fails, an old cache entry cannot grant access.

A finite link limit counts server-authorized GET and HEAD requests, not people. A database update followed by a lost response can consume a slot without an automatic refund. Browser-cached redirects that were already issued cannot be recalled by changing a link later.

Worker rate limits are best-effort counters for the code's chosen keys at Cloudflare locations. They are not strict global quotas or connection counters. Password attempts use a hashed-IP key, defaulting to five calls per 60 seconds; people sharing an exit address can share that bucket. Use distinct namespaces for separate installations.

preflight requires the expected rate-limit bindings. Manually removing AUTH_LIMITER does not guarantee every admin request will fail closed: the Admin entry point invokes that limiter only when it exists. Preserve the generated configuration and independent authentication checks. WAF rules can provide another layer, but cannot replace application permissions or validation.

Destination rules#

Targets must be validated HTTP(S) URLs. Credentials in URLs, unapproved local/private targets, the admin host, and registered short-link domains are rejected. Only reviewed query keys may be forwarded. The code does not resolve DNS while validating destinations, so hostname checks alone are not complete DNS-rebinding protection. A valid source_url is also not proof that its website is reachable or complete.

Keep private material out of a public repository#

Keep these in private storage: real deployment.json and generated account-specific Wrangler files; .env*, .dev.vars*, .local/, .wrangler/; database files and SQL backups; tokens, cookies, authentication responses, private keys, logs, and screenshots containing user data.

Review source comments, tests, Markdown, examples, offline HTML, and generated demo assets as well as obvious configuration files. .gitignore does not erase old commits. Packaging exclusions reduce accidental inclusion but are not a general secret scanner. Public documentation uses reserved example addresses, loopback addresses for local development, and explicit resource placeholders. Necessary upstream URLs and legal attributions are retained.

If a usable credential was exposed, revoke or rotate it and review access records. Removing a string from the latest source file does not invalidate that credential or remove copies from history.

Report a security problem privately#

Use the private security-reporting channel actually enabled by the repository owner. If there is none, ask for a private channel without posting the exploit or guessing a maintainer email. Include the release version, impact, and a small reproduction containing fictional data. Do not include usable credentials, real user information, or private infrastructure snapshots in a public issue.

These are implementation boundaries, not a penetration-test certificate or a promise that vulnerabilities cannot exist.

Keep database growth under control#

简体中文 · Backup and upgrade

Imagine keeping every receipt forever: the drawer gradually fills up. Linro similarly keeps audit logs, daily statistics, and revoked-token records indefinitely by default. The retention script helps you measure that drawer and prepare a small cleanup step. It does not connect to Cloudflare or delete data automatically.

1. Make a private, consistent snapshot#

Use a full D1 SQL export from the backup instructions. Restore that trusted export into a new local SQLite file, separate from any live database. For example, in a private backup directory with an unused filename:

sqlite3 review.sqlite

At the SQLite prompt:

.read Linro-backup.sql
PRAGMA quick_check;
.quit

Use the resulting binary review.sqlite file for the report. The script cannot read a plain SQL export as if it were a database. Record which database the snapshot came from and when it was exported. It contains account-related records, token verifiers, and audit details, so protect it like the original backup.

2. Read the report#

From the project root, using Node.js 22.16.0 or newer:

node scripts/retention.mjs --database /PRIVATE_BACKUP_DIR/review.sqlite

Replace /PRIVATE_BACKUP_DIR/review.sqlite with your private snapshot path. The path is an obvious placeholder, not a directory to create on a production server.

By default, the report treats no rows as eligible for cleanup. To explore a policy, add independent retention periods:

node scripts/retention.mjs --database /PRIVATE_BACKUP_DIR/review.sqlite --as-of 2026-11-21 --audit-days 180 --archive-days 365 --revoked-token-days 90 --limit 100

The date and day counts are examples. Choose them for your own operational needs.

Option Which timestamp it checks
--audit-days audit_logs.created_at, in Unix seconds
--archive-days daily_stats.date, the UTC date represented by the row
--revoked-token-days api_tokens.revoked_at, in Unix seconds

A missing period appears as null and selects zero rows. An unrevoked token is always retained, even if it has expired. Each cutoff is midnight UTC on the reference date minus the number of days. Rows exactly at the cutoff are kept. With zero days, the reference day and later dates are kept. Without --as-of, the script uses the current UTC day.

The JSON report shows total rows, eligible rows, the next batch size, allocated database bytes, and reusable pages. Per-table/index sizes are null when that SQLite build has no dbstat support. These are measurements of the local snapshot, not your live D1 account. Deleted rows can free reusable space without making the physical file smaller.

3. Generate one small cleanup statement#

For example, after reviewing the matching report:

node scripts/retention.mjs --emit-cleanup-sql audit_logs --as-of 2026-11-21 --audit-days 180 --limit 100

This prints SQL only. It opens no database and needs no credentials. Choose audit_logs, daily_stats, or api_tokens and supply the corresponding period. Keep the reference date and policy identical to the report you reviewed. Use node directly when redirecting the output into a SQL file so npm's extra output does not enter that file.

The statement selects the oldest eligible primary keys and deletes one bounded batch atomically. The default cap is 100 rows; the allowed range is 1–1,000. Finding those rows may read more rows than it deletes. Running the statement again can delete the next batch.

First test it on a disposable restored copy and rerun the report. Before any live execution, confirm the database and a current restorable backup. Each additional batch is a separate maintenance decision. For short archive retention, remember that rollup reconciles complete two-day windows and can write a recently deleted day again. No scheduled cleanup is installed by this tool.

Prepare a public Linro release#

简体中文 · Security · Licensing

A release is a clean copy for other people to download. Keep it separate from the folder that contains your real account settings and local development data. This guide describes v1.0.2.

1. Start with public templates#

Use the source folder with its unchanged placeholder deployment.example.json and both placeholder Wrangler configurations. A configured operator checkout contains real account identifiers and is not a suitable public source package.

Review all intended release files, including examples, tests, comments, Markdown, generated HTML, and demo JavaScript. Do not include real credentials, business domains, user data, private instructions, logs, backups, or historical working archives. Required public upstream links and copyright notices stay with the code.

2. Rebuild and check#

From the folder containing package.json:

npm ci
npm run check
npm test
npm run test:runtime
npm run build
npm run test:browser
npm run build:demo
npm run build:docs
npm run deploy:dry-run

build:docs regenerates docs/index.html from Markdown and copies LICENSE, NOTICE and both MIT notices byte for byte into docs/licenses/. Distribute the licenses/ directory alongside index.html for offline reading. build:demo regenerates docs/demo/ from the shared interface and the demo simulator. Include these refreshed files when committing the release. CI checks generated documentation/demo synchronization; do not edit generated HTML as a separate version of the manual.

Browser tests need a working Chrome/Chromium environment; set CFL_CHROMIUM_PATH to the installed executable if needed. Keep its sandbox enabled. An unavailable browser is an uncompleted check, not a pass. On Linux/WSL, npm run test:disconnect additionally checks real loopback disconnect behavior for Admin statistics.

The runtime suite uses the toolchain pinned in the project's dependency tree. npm run toolchain:versions displays it. A dry run packages Workers without switching production traffic; it does not prove real DNS, Access, secrets, or database behavior.

3. Stage the files to publish#

npm run package:source

The default output is release/Linro-v1.0.2/. To choose another new output directory:

npm run package:source -- --out release/Linro-v1.0.2-public

The directory must not already exist. The script uses Node built-ins and does not install dependencies, build the application, or contact Cloudflare. It selects explicit root files and permitted file types in controlled directories, rejects selected symlinks, and excludes local state, dependencies, deployment configuration, common secret files, database files, keys, recognized backup names and extensions, and ordinary generated build directories. The reviewed demo and offline docs are intentional publication assets.

The packager verifies the known hashes of the three public configuration templates. After staging, run a separate credential scan over the release directory and review the text, generated files, images, and commit history intended for publication.

4. Verify and archive the staged output#

Each staged file except the manifest itself is listed in MANIFEST.sha256. From the staged directory, on a system with sha256sum:

sha256sum -c MANIFEST.sha256

On Windows, use a compatible manifest verifier or compare every entry with Get-FileHash -Algorithm SHA256. One file hash does not verify the complete archive. A manifest detects changed bytes; it is not an author's signature.

Archive only this reviewed staged directory. After any file changes, stage again so its manifest is fresh. Keep internal review notes and execution logs outside the public package. Preserve LICENSE, NOTICE, and all inherited license texts.

If you also publish a documentation-only ZIP, give it its own manifest covering only that ZIP's files. Do not replace the full source manifest with a documentation manifest. A documentation-only archive cannot substitute for the complete source offered for the running application.

Licensing and sharing the source#

简体中文 · README · Release guide

Think of source code as the recipe for the running application. Linro's license explains when recipients and network users must be able to obtain that recipe, along with the material needed to build it.

Which license applies?#

Linro uses AGPL-3.0-only: GNU Affero General Public License version 3, without the “or any later version” option. The full LICENSE is authoritative. This page is a practical explanation, not a replacement for its terms.

Material Notice to retain
Linro as a whole AGPL-3.0-only and existing file notices
Adapted TailAdmin React interface TailAdmin MIT notice; upstream revision in NOTICE
Recharts Recharts MIT notice
Other dependencies Their own licenses and applicable notices

The third-party MIT notices do not make the entire Linro project MIT-licensed. Keep LICENSE, NOTICE, and LICENSES/*.txt intact when redistributing. The provided source and lockfile do not include ApexCharts or TailAdmin Pro; this statement is not a legal audit of every transitive dependency.

What is “Corresponding Source”?#

For a modified version used over a network, AGPL section 13 addresses offering Corresponding Source to the people interacting with it. Review the full license for your use and distribution. In practical terms, publish the source matching the actual running version, together with required build and installation material. A moving default branch may no longer describe the deployed code.

Private deployment credentials and user data are not the recipe. Publish clean templates and the lockfile, while keeping account settings, databases, passwords, and private keys out of the release. See Security and Release.

Tell Linro where that source lives#

Set source_url in your private deployment configuration. It becomes SOURCE_URL on both Workers. When present, Linro can show a source link in the dashboard and public protection pages and add a Link response header with rel="describedby".

Use a public HTTPS URL for the deployed revision or release. It must be at most 2,048 characters, have no credentials, query, fragment, whitespace, or backslashes, and use a host different from this deployment's admin and short-link hosts.

Public templates deliberately leave the value empty. Fill it before production use. preflight warns when it is empty; it does not upload source or prove that a nonempty URL is reachable, complete, reproducible, or legally sufficient. Verify the published source yourself. For a specific legal uncertainty, consult a qualified adviser using the complete license and deployment facts.
